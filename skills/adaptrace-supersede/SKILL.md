# adaptrace-supersede

バンドル（既定は `.adaptrace/`）の判断を、新しい判断に置き換える。
古い判断の本文は書き換えず、新しい判断の文書を作る。置き換える前の判断と理由を、文書として残すためである。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、ファイルごとに差分を示して承認を得る（Adaptraceの設計原則6）
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **古い判断の本文を書き換えない。** 古い判断で変えるのは `status` だけにする
- **新しい判断の理由や、検討した他の案を、推測で書かない。** 利用者に尋ねる。分からなければ、その見出しを空にして、後で書くよう伝える
- 既存の文書の `generated` は、本文の意味を変えたときだけ更新する。`status` や依存関係のキーだけを変えるときは、`generated` を変えない
- 要件の内容を変える必要があれば、ここで要件を書き換えない。変更要求として受け付けるよう案内する（skill `adaptrace-change-request`）
- コミットとpushは、利用者に頼まれたときだけ行う
- 差分は、文書ごとに示す。複数の文書の差分をまとめて示し、1回で承認を得てもよい。その場合も、どの文書を書くかを一覧にして確認する
- 利用者が、決めていない事柄を「おすすめで」と任せたときは、おすすめを案として示す。本文には、決まったこととして書かない
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace impact decisions/adr-0012-cache.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `supersedes: /decisions/adr-0012-cache.md` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける
3. `adaptrace validate` を実行し、置き換えの前からあるエラーと警告を把握しておく
4. 今の日時を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）。新しく作る文書の `generated.at` に使う

## 1. 古い判断と、新しい判断を確認する

1. 置き換える判断を特定する。利用者が名前や番号で言ったときは、`adaptrace graph --format json` の `nodes` から、`type` が判断を表す文書（`Decision`、`decision`、`ADR` など、バンドルで使っている名前）を探し、パスを確認する。`list --type` は型の名前の完全一致で、`status: deprecated` の文書も除くので、ここでは使わない
2. 古い判断の本文を読む
3. 新しい判断がすでにあるかを確認する。`adaptrace graph --format json` の `edges` で、古い判断を `supersedes` で指す文書を探す。あれば、それを新しい判断として使い、手順3の作成を省く
4. 新しい判断がまだなければ、その内容を利用者に尋ねる。すでにあれば、この質問は省く
   - 何に変えるか（決定）
   - なぜ変えるか（理由）
   - 検討した他の案
   - いつ、どこで決めたか（会議の議事録の文書があれば、そのパス）

## 2. 古い判断に依存している文書を洗い出す

**どの文書を書くよりも前に**、次の2つを実行する。`impact` は `status: deprecated` の文書を列挙しない。依存していた文書を先に中止（`deprecated`）にすると、一覧から消えてしまうためである。

- `adaptrace impact <古い判断> --format json`：見直しの連鎖（`depends_on`、`derived_from`、`satisfies`）で古い判断に届く文書。`depth` が1の文書は古い判断を直接指している。`kind` が、そのキーである。2以上の文書は、間接的に影響を受ける
- `adaptrace graph --format json`：`edges` から、`to` が古い判断の辺をすべて取り出す。`impact` に出ないキー（`blocks`、`changes`）で古い判断を指す文書も、ここで分かる。`supersedes` の辺（新しい判断から古い判断への辺）は、置き換えそのものなので、手順5で扱う対象から除く

洗い出した文書を、表にして利用者に示す。

| 文書 | 古い判断との関係 | 本文の要点 |
|---|---|---|
| `tasks/cache-warmup.md` | `depends_on`（直接） | キャッシュを起動時に温める作業 |
| `tasks/load-test.md` | 上の文書を通じて（間接） | 負荷試験 |

## 3. 新しい判断の文書を作る

差分を示し、承認を得てから書く。

- パスと名前は、既存の判断にそろえる（`adr-0012` まであれば、次は `adr-0013`）
- `type` と `state` は、既存の判断で使っている値にそろえる
- `supersedes` で古い判断を指す
- 古い判断の `satisfies`、`depends_on`、`derived_from` を引き継ぐかを、キーごとに尋ねる。新しい判断でも同じ要件を満たすなら、`satisfies` は引き継ぐ
- 会議で決めたなら、`derived_from` でその議事録の文書を指してよい
- 本文は、「決定」「理由」「検討した他の案」の見出しにする。利用者から聞いた内容だけを書く
- いつ、どこで決めたかは、「決定」の最初の1文に書く（例：「2026-04-08の設計会議で決めた」）。議事録の文書があれば、本文から相対パスでリンクする
- 決定の一部がまだ決まっていないと利用者が言ったときは、「未決事項」の見出しを追加し、利用者が挙げた事柄だけを書く。利用者が見出しを空にするよう求めたら、それに従う
- 新しい判断の題とファイル名は、差分の中で示し、利用者の確認を得る。題は判断の中身そのものなので、推測で確定しない

```yaml
---
type: Decision
title: ADR-0013 セッションの保存先をデータベースにする
state: accepted
supersedes: /decisions/adr-0012-cache.md
satisfies: /requirements/req-4-session.md
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---
```

- 新しい文書は、`decisions/index.md` に `* [表示名](ファイル名)` の形で1行のリンクを追加する

## 4. 古い判断を廃止する

古い判断のフロントマターに `status: deprecated` を追加する差分を示し、承認を得てから書く。本文と、ほかのキーは変えない。`generated` も変えない。

- `decisions/index.md` の古い判断へのリンクは、削除も変更もしない。`index.md` と `log.md` には、行を追加するだけにする

## 5. 依存していた文書を、1件ずつ決める

手順2の表の、古い判断を**直接**指している文書ごとに、次のどれにするかを尋ねる。本文を読んで、おすすめと理由を添える。

| 扱い | 向いている場合 | 変更 |
|---|---|---|
| 付け替える | 新しい判断の下でも、その文書が必要 | キーの値を、古い判断から新しい判断のパスに変える |
| 外す | 新しい判断とは関係がなくなった | キーから古い判断を削除する。キーが空になれば、キーごと削除する |
| 中止する | 古い判断を実現するための作業で、もう要らない | `state` を中止の値にするか、`status: deprecated` にする。バンドルに中止を表す値がなければ、どちらにするかを尋ねる |
| そのままにする | 経緯として古い判断を指しておきたい | 変更しない |

- 1つの文書に1つの差分を示し、承認を得てから書く。変えるのは、決めたキーだけにする。`generated` は変えない
- 付け替えた文書は、新しい判断に合わせて見直す必要がある。新しい判断の方が新しければ、`adaptrace stale` で見直しの対象として示される。新しい判断がすでにあり、付け替えた文書より古い場合は、`stale` には出ない。どちらの場合も、手順6で見直しの対象として報告する
- `changes` で古い判断を指す未決の変更要求は、変更しない。変更要求の起点が廃止されたことを、報告に書く。変更要求の扱いは、人が決める
- 間接的に影響を受ける文書（`depth` が2以上）は、ここでは変更しない。手順6で、見直しの対象として報告する
- 中止したタスクを `state` の値で記録すると、それに依存するタスクは、`board` で「待っている」と表示され続ける。`status: deprecated` なら、表示されない。中止したタスク自身が `blocks` でほかのタスクを指していれば、その `blocks` を外すかも尋ねる。`status: deprecated` にすると、`board` にも `health` にも表れなくなるため。どちらの場合も、依存するタスクがあれば、その `depends_on` を外すか、付け替えるかも尋ねる。間接的に影響を受ける文書でも尋ねてよいが、変更するのは利用者が変更を選んだときだけにする

## 6. 記録して報告する

1. `log.md` に記録するかを尋ねる。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、新しい判断を作ったことを `* **Creation**: <説明>`、古い判断の廃止と依存していた文書の扱いを `* **Update**: <説明>` の形で書く
2. `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す
3. `adaptrace stale` を実行する
4. 次をまとめて報告する。報告は会話の中で行い、ファイルには書かない
   - 新しい判断と、廃止した古い判断
   - 依存していた文書ごとの扱い（付け替えた、外した、中止した、そのまま）
   - 見直しが要る文書：付け替えた文書と、間接的に影響を受ける文書。見直しは、skill `adaptrace-review` で進められる
   - 古い判断を `changes` で指す変更要求と、ほかに人が決めること
