# adaptrace-risk

バンドル（既定は `.adaptrace/`）のリスクを、1件ずつ利用者と見直し、結果を記録する。
対象は、見直し時期（`stale_after`）を過ぎたリスクと、依存先（判断など）がリスクより後に更新されたリスクである。
評価や扱いは人が決める。このskillは、材料と選択肢を示し、決まったことを記録する。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、差分を示して承認を得る（Adaptraceの設計原則6）
- 差分は、文書ごとに示す。複数の文書の差分をまとめて示し、1回で承認を得てもよい。その場合も、どの文書を書くかを一覧にして確認する
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **リスクの評価、扱い、次の見直し日を、自分で決めない。** 材料と選択肢を示し、利用者が決める。推測で評価を書かない
- 評価のキー（発生の可能性、影響など）と `state` の値は、バンドルの既存のリスクで使っているものにそろえる。新しいキーは、利用者が決めたときだけ追加する
- 書き換えてよいのは、次だけにする。ほかの文書は変えない
  - 見直すリスクの文書
  - 対応策として新しく作るTaskの文書と、その型の `index.md` への1行の追加
  - `log.md`：行を追加するだけ
- 対応策のタスクは、利用者が題、担当、期日を決めたときだけ作る。推測で埋めない
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace impact risks/idp-lock-in.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `derived_from: /risks/idp-lock-in.md` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確認し、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。なければ、利用者に尋ねる。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける
3. `adaptrace validate` を実行し、見直しの前からあるエラーと警告を把握しておく
4. 今の日時を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）。`verified.at` と `generated.at` に使う
5. 見直しを判断する人のIDを尋ねる（例：`sato`）。見直したリスクの `verified` と `generated` の `by` に使う（`human:<ID>`）。リスクの評価は人の判断なので、本文をエージェントが書いても、`by` は判断した人にする。`by` は、既存の文書の書き方にそろえる。新しく作るタスクの `generated.by` は、「共通の書き方」に従い、作業したエージェントにする

## 1. 見直すリスクを決める

1. `adaptrace list --format json --columns type,state`：型の名前と `state` の値を確認する。リスクの型（`Risk` など）と、リスクで使っている `state` の値（`open`、`closed` など）を控える。`state` が空文字（`""`）の文書は、`state` を持たない
2. `adaptrace stale --format json`：`stale` から、リスクの型の文書を取り出す。`stale` の結果には型と `state` がないので、手順1の1の結果とパスで突き合わせる。`state` が閉じた値のリスクは、見直しの対象にしない。閉じた値は、既存の値の名前（`closed` など）から判断し、分からなければ利用者に尋ねる。`stale` に出る閉じたリスクがあれば、報告に書く。`reasons` の `kind` が理由である
   - `expired`：見直し時期（`staleAfter`）を過ぎた
   - `older-than-dependency`：依存先（`dependency`）が、リスクより後に更新された
   - そのほかの理由（ファイルの変更など）も、そのまま示す
3. 利用者が名前を挙げたリスクがあれば、それも対象にする。見つからなければ、推測せずに尋ねる
4. 対象のリスクを、表で示す。見直す順番を利用者と決める。決まりがなければ、見直し時期を過ぎたリスクを、期限の古い順に並べる。その後に、依存先が更新されたリスクを、依存先の更新日時の古い順に並べる

| リスク | 状態（`state`） | 理由 | 期限か、更新された依存先 |
|---|---|---|---|
| `risks/idp-lock-in.md` | `open` | 見直し時期を過ぎた | 2026-11-24 |

## 2. 1件ずつ見直す

リスクごとに、次を行う。

1. リスクの本文と、フロントマターを読む。評価のキー（`probability`、`impact` など、名前はバンドルによる）と担当（`owner`）を確認する
2. 依存先が更新されたリスクなら、その依存先の文書を読み、何が変わったかを要約する。gitの履歴があれば、`git log -p -- <依存先のファイル>` で、リスクの最終更新より後の変更を確認する。確認できなければ、「何が変わったかは確認できない。今の内容は次のとおり」と伝え、変わった内容を断定しない
3. `adaptrace graph --format json` の `backlinks` で、そのリスクを指している文書（対応策のタスクなど）を確認する。対応策の進み具合も材料として示す
4. 材料を示し、扱いを尋ねる。おすすめと理由を添えてよい

| 扱い | 向いている場合 | 変更 |
|---|---|---|
| 変更なしで続ける | 評価も本文も今のままでよい | `verified` に見直した記録を追加する。`stale_after` を次の見直し日にする。`generated` と本文は変えない。依存先が更新されたリスクも、`verified` の日時が依存先の更新より新しくなるので、`stale` に出なくなる |
| 評価や本文を更新する | 発生の可能性、影響、対応方針などが変わった | 決めたキーと本文を変える。`generated` を今の日時にする。`stale_after` を次の見直し日にする |
| 対応策のタスクを作る | 新しい対応が必要になった | 新しいTaskの文書を作る。上の2つのどちらかと組み合わせる |
| 閉じる | 原因がなくなった、期間が過ぎたなど、リスクではなくなった | `state` を閉じた値にする。`stale_after` を削除する。`generated` を今の日時にし、閉じた理由を本文に書く。`depends_on` などの依存関係は、経緯として残す。依存先が後で更新されると `stale` に出るが、閉じたリスクは見直しの対象にしない（手順1の2） |
| 顕在化した | リスクが起きた | `state` を顕在化を表す値にする。`generated` を今の日時にし、起きたことを本文に書く。`stale_after` は、対応が終わるまで見直す日にするか、削除するかを尋ねる。対応は、変更要求（skill `adaptrace-change-request`）や課題として扱うよう案内する |

5. 次の見直し日を尋ねる。既存のリスクの `stale_after` と最終更新の間隔から、案を示してよい。決めるのは利用者である。「2週間後」のような言い方は、今日から数える。`stale_after` は、タイムゾーン付きのISO 8601の日時で書く（`validate` の決まり）。時刻とタイムゾーンは、既存の値にそろえる。既存の値が日付だけなら、`validate` が警告することを伝える
6. `state` の値は、手順1の1で控えた値にそろえる。閉じた値や顕在化を表す値がなければ、候補（`closed`、`occurred` など）を示して利用者に確認する。評価のキーの値も、既存のリスクで使っている値にそろえる。既存の値が「中」「低」のように段階の一部なら、同じ段階の値（「高」）は使ってよい。段階が分からない新しい値は、利用者に確認する

### 記録の書き方

- `verified` は、1件なら `verified: { by: human:<ID>, at: <日時> }` と1行で、`generated` の次の行に書く。すでにあれば、それまでの記録を残し、ブロック形式のリストにして末尾に追加する
- `verified` を書くのは「変更なしで続ける」ときだけにする。評価や本文を更新したとき、閉じたときは、`generated` を今の日時にすれば見直した記録になる。既存の `verified` は消さない
- 評価のキーを変えるときは、値だけを変える。キーの位置は変えない
- 本文に追記するときは、見直した日と、変えた理由を書く。書くのは、利用者から聞いた内容と、依存先の文書に書いてある事実だけにする。依存先の事実を書くときは、その文書を示す（例：「ADR-0002によると」）。「先週」のような相対的な言い方は、今日の日付から日付に直して書くか、利用者に確認する

### 対応策のタスク

- 題、担当（`owner`）、期日（`due`）を利用者に尋ねる。決まらない項目は書かない。題が決まらなければ、タスクを作らずに報告に書く
- パスと名前は、既存のタスクにそろえる。既存のタスクが少なくて決まりが読み取れなければ、題を表す短い英語の名前にして、差分で示す。本文は、見出しだけにするか、利用者から聞いた内容だけを書く
- `derived_from` でリスクを指す。`state` は、既存のタスクで着手前を表す値にする。着手前を表す値が既存のタスクになければ、候補（`to_do` など）を示して利用者に確認する
- `generated` は、手順0で取得した日時と、作業したエージェントにする（「共通の書き方」）
- 型の `index.md` があれば、`* [表示名](ファイル名)` の形で1行を追加する

```yaml
---
type: Task
title: SMSの送信件数に上限を設ける
owner: suzuki
state: to_do
due: 2026-12-10
derived_from: /risks/sms-cost.md
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---
```

## 3. 書く

1. すべてのリスクの扱いを決めてから、手順2で決めた変更を、文書ごとに差分で示し、まとめて承認を得てから書く。利用者がリスクごとに書くことを望めば、それに従う
2. `log.md` に記録するかを、最後に1回だけ尋ねる。この手順の1の差分と一緒に尋ねてよい。追加する場合は、今日の日付で見出し（`## YYYY-MM-DD`）を作り、その下に`* **Update**: <説明>` の形で、この作業全体を1行で書く。タスクを作ったなら、`* **Creation**: <説明>` の行も書く
3. `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す
4. `adaptrace stale --format json` をもう一度実行し、見直したリスクが出ないことを確認する。出るリスクがあれば、理由を報告する。評価や本文を更新したリスクに依存している文書（対応策のタスクなど）が、新しく出ることがある。リスクの内容が変わったためで、見直しが要るかを報告に書く

## 4. 報告する

次をまとめて報告する。報告は会話の中で行い、ファイルには書かない。

- リスクごとの扱いと、次の見直し日
- 作ったタスクと、その担当と期日
- 閉じたリスクと、顕在化したリスク。顕在化したリスクで、人が行う対応
- 見直さなかったリスク（利用者が後回しにしたもの）と、まだ `stale` に出るリスク。更新したリスクに依存していて、新しく `stale` に出た文書
- 手順0の時点より増えた `validate` のエラーと警告
