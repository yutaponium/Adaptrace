# adaptrace-minutes

議事録から、Adaptraceのバンドル（既定は `.adaptrace/`）の文書を作り、既存の文書を更新する。
議事録は、まず `type: Meeting` の文書としてバンドルに置き、作った文書は `derived_from` でそれを指す。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
CLIの `adaptrace extract` の仕様（同じファイルの「議事録からの抽出」）も、文書の作り方の参考になる。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、ファイルごとに差分を示して承認を得る（Adaptraceの設計原則6）
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **議事録に書いていないことを、推測で埋めない。** 担当、期日、`state` は、議事録に書いてあるものだけを使う。分からなければ尋ねるか、空のままにする
  - 担当は、既存の文書で使っている `owner` の書き方にそろえる（議事録の「伊藤」を `ito` にするなど）。対応が分からなければ尋ねる
  - 年のない期日（「6月2日」）は、会議の日以後で最も近い日にする（12月の会議の「1月15日」は翌年）。補ったことを、手順2の確認の表に書く
- 議事録の「検討した」「意見が出た」は、決まったことではない。決まったことと、決まっていないことを分ける
- **連絡先をバンドルに書かない。** メールアドレス、電話番号、署名は、議事録の文書にも、ほかの文書にも書かない
- 要件や範囲を変える要望は、このskillで要件を書き換えない。変更要求として受け付けるよう案内する（skill `adaptrace-change-request`）
- 新しい文書の `generated.at` には、手順0で取得した日時を使う
- 既存の文書の `generated` は、本文の意味を変えたときだけ更新する。`state`、`owner`、`due`、`status` だけを変えるときは、`generated` を変えない。`generated.at` は内容の最終更新であり、これを新しくすると、依存する文書が見直しの対象になるため
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace impact decisions/adr-0004-stock.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `derived_from: /meetings/2026-05-12-stock.md` |
| 本文のリンク（参照） | その文書からの相対パス | `[在庫の引当](../tasks/stock-allocate.md)` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける。バンドルがなければ、先に既存の文書を取り込む必要があると伝える（skill `adaptrace-adopt`）
3. 今の状態を調べる
   - `adaptrace validate`：取り込みの前からあるエラーと警告を把握しておく
   - `adaptrace list --format json --columns type,status,state,owner,due`：既存の文書。重複の確認と、更新する文書の特定に使う。`list` は `status: deprecated` の文書を除くので、`--status deprecated` を付けてもう一度実行し、置き換えた判断なども確認する
   - `adaptrace board --format json`：タスクの `state` に使っている値（列の名前）。`board` は、使われている値しか列にしない。まだ始めていないことを表す値がなければ `to_do`、終わったことを表す値がなければ `done` を使う。どちらも `board` の既定の値である
4. 今の日時を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）

## 1. 議事録をバンドルに置く

議事録は、バンドルの中の `type: Meeting` の文書か、バンドルの外のファイル、または会話に貼り付けた文面で受け取る。

- **バンドルの中にある場合**：その文書を使う
- **同じ会議の下書きがある場合**：議事録がバンドルの外にあっても、`meetings/` に同じ会議の `Meeting` の文書がないかを、まず確認する。skill `adaptrace-weekly` は、`meetings/<会議の日>-weekly.md` に `status: draft` の下書きを作る。あれば、新しく作らず、その下書きの「決まったこと」「宿題」の見出しに、議事録の内容を追記する差分を示す。議事録が確定していれば、`status: draft` を外すかも尋ねる
- **どちらでもない場合**：議事録の文書を新しく作る差分を示す
  - パスは `meetings/<会議の日>-<会議の名前>.md`。`<会議の名前>` は、英小文字、数字、`-` で短く書く（定例なら `weekly`、キックオフなら `kickoff`）。同じパスがあれば、`-2`、`-3` を付ける
  - フロントマターは `type: Meeting`、`title`（会議の名前と日付）、`generated`。依存関係のキーは付けない
  - 本文は、議事録の内容をそのまま写す。ただし、連絡先と署名は除く。除いたことを利用者に伝える
  - 会議の日が議事録から分からなければ、尋ねる。今日の日付にはしない
  - `meetings/index.md` に、`* [表示名](ファイル名)` の形で1行のリンクを追加する。`meetings/` がなければ、`meetings/index.md` を作り、ルートの `index.md` にもリンクを追加する

```yaml
---
type: Meeting
title: 在庫管理の定例（2026-05-12）
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---
```

議事録の文書は、承認を得て最初に書く。後の手順で作る文書が、`derived_from` でこれを指すためである。

## 2. 議事録を読み、項目に分ける

議事録の内容を、次のどれかに分ける。1つの発言から、複数の項目ができることもある。

| 区分 | 例 | 手順 |
|---|---|---|
| 新しい文書 | 決まったこと（`Decision`）、割り当てられた作業（`Task`）、懸念として挙がったリスク（`Risk`）、期日の決まった節目（`Milestone`）、合意した要件（`Requirement`）、受け入れの基準（`Acceptance`） | 手順3 |
| 既存の文書の更新 | タスクが終わった、担当や期日が変わった、判断を置き換えた、リスクがなくなった | 手順4 |
| 変更要求にするもの | 顧客や利用者からの、要件や範囲を変える要望 | 手順5で案内する |
| 文書にしないもの | 報告だけで決まったことがない、検討中、雑談 | 報告に書くだけ |

- 新しい文書の候補ごとに、既存の文書に同じものがないかを確認する。あれば、新しく作らず、既存の文書の更新として扱う
- リスクは、決定がなくても文書にしてよい。「〜のおそれがある」「〜が必要になりそう」のような懸念は、リスクの候補にする
- 「確認する」「調べる」のような宿題は、担当がいなくてもタスクの候補にする。`owner` は空のままにし、担当を尋ねる
- 分けた結果を表にして、利用者に確認する。表には、議事録の該当する文（根拠）と、文書の型、作るか更新するかを書く。補った値（年、`owner` の書き方）も書く。採否は、利用者が決める（複数選択で尋ねる）
- 同じ確認で、新しい文書に `status: draft` を付けるかも尋ねる（手順3）
- `Requirement` を新しく作るのは、議事録で要件として合意したときだけにする。要望が出ただけなら、変更要求にするものとして扱う

## 3. 新しい文書を作る

採用した項目ごとに、文書の差分を示し、承認を得てから書く。

- パスは `<型のディレクトリ>/<id>.md`（`requirements`、`acceptance`、`decisions`、`tasks`、`risks`、`milestones`）。既存の文書と同じ名前の付け方にする（`adr-0003` まであれば、次は `adr-0004`）
- 型は、バンドルで使っている名前にそろえる
- フロントマター
  - `derived_from: /meetings/<議事録>.md`
  - `status: draft`。議事録から起こした案であり、内容を人が確認してから外す。`adaptrace extract` と同じ扱いである。利用者が、会議で確定したので不要と答えたら、付けない。利用者が判断を任せたら、付ける方を勧める
  - タスクの `state` は、バンドルで使っている、まだ始めていないことを表す値にする（`board` の列の名前から選ぶ）。`owner` と `due` は、議事録に書いてあるときだけ書く
  - 既存の文書との依存関係（`depends_on`、`satisfies` など）は、議事録か、既存の文書の本文から読み取れるときだけ候補として示す。根拠も示す
  - リスクの `state`、発生の確率、影響の大きさは、議事録に書いてあるときだけ書く
- 本文は、議事録の該当する内容の要点にする。議事録へのリンクを、相対パスで書いてよい

```yaml
---
type: Task
title: 倉庫ごとの在庫の引当を実装する
status: draft
state: to_do
owner: ito
due: 2026-05-26
derived_from: /meetings/2026-05-12-stock.md
depends_on: /decisions/adr-0004-stock.md
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---
```

- 新しい文書は、そのディレクトリの `index.md` に1行のリンクを追加する。新しいディレクトリを作ったら、そのディレクトリの `index.md` を作り、ルートの `index.md` にもリンクを追加する

## 4. 既存の文書を更新する

採用した項目ごとに、既存の文書の差分を示し、承認を得てから書く。変えるのは、議事録で決まったことだけにする。

判断を置き換えるときは、**どの文書を書くよりも前に** `adaptrace impact <古い判断>` を実行する。`impact` は `status: deprecated` の文書を列挙しないので、同じ取り込みで中止したタスクなどを先に書くと、古い判断に依存していた文書として見えなくなる。示された文書（タスクなど）ごとに、新しい判断に合わせて見直しが要るかを、差分と一緒に示す。依存先を書き換えるのは、利用者が承認したときだけにする

| 議事録の内容 | 更新 |
|---|---|
| タスクが終わった、担当や期日が変わった | そのタスクの `state`、`owner`、`due` |
| 作業をやめた | 中止の記録の方法を尋ねる（下の注意） |
| 判断を置き換えた | 新しい判断の文書を作り、`supersedes` で古い判断を指す。古い判断は `status: deprecated` にする。古い判断の本文は書き換えない。古い判断の `satisfies` や `depends_on` を、新しい判断に引き継ぐかを、差分の中で確認する |
| リスクがなくなった、対策が決まった | そのリスクの `state` か本文。リスクの対策を新しいタスクにするなら、手順3で作る |

- 変えるキーのほかは変えない。`generated` は、本文の意味を変えたときだけ更新する（「守ること」）
- 中止の記録には、次の2つがある。バンドルに中止を表す `state` の値があれば、それを使う。なければ、違いを示して尋ねる
  - `status: deprecated`：`board` の列、`list`、`impact` に出なくなる。終わった話として、一覧から外したいときに向く。依存するタスクも、`board` で待っていると表示されなくなる
  - 新しい `state` の値（`cancelled` など）：一覧に残る。`board` は、`state` が終わったことを表す値（`done` など）でない依存先を待つので、依存するタスクは「待っている」と表示され続ける
  - どちらの方法でも、中止したタスクに依存するタスクがあれば、その `depends_on` を外すか、付け替えるかを尋ねる。中止したタスク自身が `blocks` でほかのタスクを指していれば、その `blocks` を外すかも尋ねる。`status: deprecated` にすると、`board` にも `health` にも表れなくなるため
- 要件の内容を変える決定は、ここで要件を書き換えない。手順5で、変更要求にするよう案内する

## 5. 記録して報告する

1. `log.md` に記録するかを尋ねる。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Creation**: <説明>` や `* **Update**: <説明>` の形で、新しい順に書く
2. `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す
3. 次をまとめて報告する。報告は会話の中で行い、ファイルには書かない
   - 議事録の文書と、作った文書、更新した文書
   - 採用しなかった項目と、文書にしなかった項目
   - 変更要求にするもの。依頼者と受け付けの日時を確認して、skill `adaptrace-change-request` で受け付けるよう案内する。まだ正式に受け付けていない要望なら、受け付けるときに使うよう案内する
   - 置き換えた判断の影響（手順4の初めに実行した `impact` の結果）と、見直しが要る文書。見直しは、skill `adaptrace-review` か、利用者が別に行う
   - `status: draft` で作った文書は、内容を確認してから `status: draft` を外すこと
