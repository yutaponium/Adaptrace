# adaptrace-health

バンドル（既定は `.adaptrace/`）の依存関係を、利用者と整理する。
検出は `adaptrace health` と `adaptrace validate` が行う。このskillは、検出された項目ごとに扱いを利用者と決め、承認された修正だけを書く。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、ファイルごとに差分を示して承認を得る（Adaptraceの設計原則6）
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **`health` の項目は、どれもエラーではない。** 残す理由があれば、そのままにしてよい。おすすめを示しても、決めるのは利用者である
- 依存関係を新しく張るときは、根拠を示す。根拠は、両方の文書の本文か、利用者の説明である。推測で張らない
- 変えるのは、扱いを決めた項目のキーだけにする。本文は書き換えない。キーの書き方（リストか1つの値か、キーの順序）は、その文書と既存の文書にそろえる。値が1つになったリストは、リストのままでよい
- 依存関係のキーは、依存する側の文書に書く。たとえば、判断から導かれたリスクなら、リスクの文書に `derived_from` を書く
- 既存の文書の `generated` は変えない。依存関係のキーや `status` だけを変えても、本文の意味は変わらないため。`generated` を変えると、依存する文書が見直しの対象になる
- コミットとpushは、利用者に頼まれたときだけ行う
- 差分は、文書ごとに示す。複数の文書の差分をまとめて示し、1回で承認を得てもよい。その場合も、どの文書を書くかを一覧にして確認する
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace impact decisions/adr-0002-db.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `depends_on: /decisions/adr-0002-db.md` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確認し、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける

## 1. 項目を集めて、整理する範囲を決める

1. 次の3つを実行し、結果を手順4で比べるために、会話の中に控えておく
   - `adaptrace validate --format json`：エラーと警告の配列。`severity`（`error` か `warning`）と `code` がある。エラーかどうかは、終了コードではなく `severity` で判断する
   - `adaptrace health --format json`：依存関係を整理する提案の配列。`severity` はなく、どれもエラーではない。終了コードは常に0。`orphan` には `line` がない。`deprecated-target` と `redundant-dependency` には、対象の依存のキー（`kind`）と依存先（`to`）がある。`deprecated-target` には `replacedBy`、`redundant-dependency` には `via` がある。JSONのパスは、先頭に `/` が付かない。フロントマターに書くときは、先頭に `/` を付ける
   - `adaptrace stale --format json`：依存先より古い文書。整理の後に新しく出た文書を見分けるため
2. 項目を、次の区分ごとに数えて、表で示す

   | 区分 | 項目（`code`） | 扱い |
   |---|---|---|
   | 修正が必要なエラー | `validate` の `error`（`dependency-cycle`、`dependency-target` など） | 修正するまで `validate` が失敗する |
   | デッドロック | `dependency-deadlock`（`validate` の警告） | 互いに待っていて、どちらも始められない。警告なので `validate` は失敗しないが、作業が止まる |
   | 廃止した文書への依存 | `deprecated-target` | 付け替える、外す、経緯として残す |
   | 冗長な依存 | `redundant-dependency` | 外すか、直接の関係を明示するために残す |
   | 孤立した文書 | `orphan` | 依存関係を張る、廃止する、そのままにする |
   | そのほかの警告 | `validate` の `warning` のうち、`dependency-deadlock` 以外 | 下の「そのほかの警告」 |

3. `validate` と `health` の項目が合わせて少ないとき（目安は10件以下）は、「2. 項目ごとに扱いを決める」のおすすめを全件まとめて示し、扱いを一度に尋ねてよい
4. 項目が多いときは、どの区分から整理するかを尋ね、区分ごとに進める。おすすめは、上の表の順である。エラーとデッドロックは作業を止めるので、先に片付ける。1回の作業で全部を終えなくてよい

## 2. 項目ごとに扱いを決める

区分の項目ごとに、関係する文書の本文を読み、おすすめの扱いと理由を添えて尋ねる。まとめて尋ねるときも、項目ごとにおすすめと理由を示す。扱いが決まっても、まだ書かない。差分は手順3で示す。

### デッドロック（`dependency-deadlock`）

- `message` に、互いに待っている文書と、そのキーが書いてある。`blocks` は、指す側が終わるまで、指された側が始められないことを表す
- 1つの文書が、同じ相手を `depends_on` と `blocks` の両方で指しているときは、書き間違いのことが多い。どちらが実際の順序かを尋ね、もう一方を外す案を示す
- 2つ以上の文書が互いを待っているときは、どの依存が実際の作業の順序と合っていないかを、本文と `state` から考え、外す依存のおすすめを示す。作業の一部を先に始められるなら、文書を分ける案も示す
- 片方の `state` がすでに終わりの値でも、実際の待ちはないが、依存関係の矛盾は残る。解消を勧める

### 循環依存（`dependency-cycle`）

- 見直しの連鎖のキー（`depends_on`、`derived_from`、`satisfies`）か `supersedes` で、文書が互いを指している
- どれか1つの依存を外せば解消する。どれを外すかは、上流と下流の関係（要件から判断、判断からタスク）から考えて示す

### 廃止した文書への依存（`deprecated-target`）

| 扱い | 向いている場合 | 変更 |
|---|---|---|
| 付け替える | 置き換えた文書（`replacedBy`）の下でも、依存が必要 | キーの値を、`replacedBy` の文書のパスに変える。同じキーにその文書がすでにあれば、廃止した文書の記述を外すだけにする |
| 外す | 置き換えた文書とは関係がない | キーから削除する。キーが空になれば、キーごと削除する |
| 経緯として残す | 廃止した文書を指しておきたい | 変更しない |

- `message` が「This document replaces it」で始まる文を含むときは、この文書自身が廃止した文書を置き換えている。付け替える先はないので、外すか、経緯として残すかだけを尋ねる
- `replacedBy` が複数あれば、どれに付け替えるかを尋ねる。空なら、付け替える先を利用者に尋ねる
- 付け替えた文書は、新しい依存先に合わせて見直す必要がある。新しい依存先の `generated.at` の方が新しければ、`adaptrace stale` に示される。報告で、見直しの対象として示す。見直しと、その記録（`verified`）は、このskillでは行わない。利用者が、すでに新しい依存先に合わせてあると言った場合も同じである

### 冗長な依存（`redundant-dependency`）

- `via` が空なら、同じ文書を同じキーに2回書いている。重複した記述を外す
- `via` があれば、同じキーのより長い経路でも届く。外しても、依存先を変えたときに `impact` が届く文書は変わらない。ただし、`stale` は直接の依存先とだけ比べる。外した後は、依存先が変わると、まず経路の途中の文書が古いと示され、それを見直すとこの文書が示される。利用者にこの違いを伝える
- 本文が、その依存先の内容に直接触れていれば、直接の関係を明示するために残す案を示す。触れていなければ、外す案を示す

### 孤立した文書（`orphan`）

| 扱い | 向いている場合 | 変更 |
|---|---|---|
| 依存関係を張る | 本文や利用者の説明から、関係する文書がある | 適切なキーで、関係する文書を指す |
| 廃止する | もう要らない | `status: deprecated` を追加する。`state` は変えない。`state` が進行中の値なら、作業を止めてよいかを確認する |
| そのままにする | どの文書にも依存しない、独立した文書（全体に共通する方針など） | 変更しない |

- 既存の文書の `state` に、中止を表す値（`cancelled` など）が使われていれば、`status: deprecated` の代わりにその値にするかを尋ねる。使われている値は、`adaptrace graph --format json` の `nodes` の `state` で分かる。`list` は、既定で `deprecated` の文書を表示しないので、ここでは使わない。`status: deprecated` のタスクは、`board` に表示されない
- 依存関係を張る候補は、関係しそうな文書の本文を読んで探す。文書が多いときは、`adaptrace graph --format json` の `nodes` の型と表示名から絞り込む。根拠を添えて示す
- キーは、依存する側の文書に書く。孤立した文書が下流（タスク、リスクなど）なら、孤立した文書の側に書く。上流（要件、判断、議事録など）なら、それに依存する下流の文書の側に書く
- キーの選び方：判断やリスクなどの文書から導かれたなら `derived_from`、要件を満たすなら `satisfies`、ほかの文書の完了や内容を前提にするなら `depends_on`

### そのほかの警告

- `missing-generated`：最終更新がない。日時を推測で書かない。gitの履歴から移行するなら `adaptrace migrate-dates` を案内する
- `stale-generated`：本文を変えたのに、`generated` も `verified` も変わっていない。本文の意味を変えたなら `generated` を、言い回しだけなら `verified` を更新する。どちらかを利用者に尋ねる
- 上にない警告は、`message` を示し、修正の案を差分で示す

## 3. 修正する

1. 扱いを決めた項目の差分を、文書ごとに示し、承認を得てから書く。「2. 項目ごとに扱いを決める」で扱いを決めても、差分の承認は別に得る。承認した差分にないキーは追加しない
2. 変えるのは、決めたキーだけにする。`generated` は変えない（「そのほかの警告」の `stale-generated` を除く）
3. `index.md` は、依存関係の整理では変えない。文書を廃止しても、リンクは残す。`log.md` には、行を追加するだけにする。既存の行は変えない

## 4. 記録して報告する

1. `adaptrace validate`、`adaptrace health`、`adaptrace stale` を実行する。手順1で控えた結果と比べ、手順1になかった項目があれば、原因を説明して、修正の差分を示す。`stale` に新しく出た文書は、付け替えた文書などで、見直しの対象である
2. `log.md` に記録するかを、追加する行の差分で尋ねる。今日の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Update**: <説明>` の形で書く。見出しは新しい順に並べるので、今日の見出しがなければ、既存の日付の見出し（`## YYYY-MM-DD`）より上に作る。ファイルの題（`# ...`）より上には置かない。見出しがすでにあれば、その下の先頭に追加する。書いた後に `adaptrace validate` を実行する
3. 利用者の返事の後に、次をまとめて報告する。報告は会話の中で行い、ファイルには書かない。この報告を、作業の最後の返答にする
   - 区分ごとの、修正した項目と、そのままにした項目
   - そのままにした項目は、次に `health` を実行したときにも示されること
   - 見直しが要る文書：依存先を付け替えた文書と、新しく依存関係を張った文書。どちらも、新しい依存先の方が新しいときだけ `stale` に出るが、`stale` に出なくても、依存先と内容が合っているかを確認する。見直しは、skill `adaptrace-review` で進められる
   - 冗長な依存を外した文書：依存先が変わったとき、`stale` には経路の途中の文書が先に示されること
   - まだ扱っていない区分と、その件数
