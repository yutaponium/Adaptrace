# adaptrace-change-request

依頼の文面から、Adaptraceのバンドル（既定は `.adaptrace/`）に変更要求の文書を作る。
そのうえで、影響範囲の見積もりと、重なる未決の変更要求を示し、判断の材料をそろえる。
手順は、Adaptraceのガイド「PMBOKの文書を変更要求に合わせて更新する」（`docs/guide/pmbok.md`）の「3. 変更要求を受け付ける」に従う。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、ファイルごとに差分を示して承認を得る（Adaptraceの設計原則6）
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **変更要求を承認、却下しない。** `state` は受け付けの値にする。判断は人が行う。このskillが示す見積もりと判定は、判断の材料である
- 依頼の文面にない事実（依頼者の所属、受け付けた日時、起点など）を、推測で埋めない。分からなければ尋ねる
- **連絡先をバンドルに書かない。** メールアドレス、電話番号、署名は、変更要求の文書にもステークホルダーの文書にも書かない
- 影響の見積もりや、ほかの変更要求との判定は、社内の検討である。変更要求の文書には書かず、利用者への報告に書く。変更要求の文書は、受け付けた依頼の記録にする
- 既存の文書（ほかの変更要求、要件、判断など）は変更しない。変更が必要だと思ったら、報告に書く
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace estimate --request change-requests/cr-011-csv-export.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `changes: /requirements/req-7-report.md` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確認し、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける。バンドルがなければ、先に既存の文書を取り込む必要があると伝える（skill `adaptrace-adopt` か、ガイド「既存のリポジトリにAdaptraceを導入する」）
3. 今の状態を調べる
   - `adaptrace validate`：受け付けの前からあるエラーを把握しておく
   - `adaptrace list --type "Change Request" --format json --columns state,requested_by,received_at,changes`：既存の変更要求。型の名前は、バンドルで使っている名前にそろえる
   - 既存の変更要求で、`state` に使っている値を確認する。決着を表す値（承認、却下など）が、`conflicts` の既定（`approved`、`accepted`、`rejected`、`deferred`、`implemented`、`closed`、`done`）と違えば、利用者に確認して、手順6の `conflicts` に `--settled <値,...>` を付ける
   - `adaptrace list --format json --columns type,side,role`：ステークホルダーの文書（`type` が `Stakeholder` か、`side` を持つ文書）と、起点の候補になる文書
4. 今の日時を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）。今回作る文書の `generated.at` には、すべてこの値を使う

## 1. 依頼を読む

依頼は、会話に貼り付けた文面か、ファイル（保存したメールなど）で受け取る。

次のことを読み取り、表にして利用者に確認する。

| 項目 | 読み取る場所 | 分からないとき |
|---|---|---|
| 何を求めているか | 本文 | 利用者に尋ねる |
| 依頼者 | 差出人、署名、本文 | 利用者に尋ねる |
| 受け付けた日時 | メールの `Date:`、チャットの投稿日時 | 利用者に尋ねる。今の日時にはしない |
| 1件か複数か | 本文 | 求めていることが複数あれば、1件1ファイルに分けることを提案する |

- 受け付けた日時は、`2026-03-04T09:30:00+09:00` の形にする。メールの `Date:` のタイムゾーンをそのまま使う
- 既存の変更要求に、同じことを求めている変更要求がないかを確認する。あれば、新しく作るか、既存の変更要求の記録として扱うかを尋ねる

## 2. 起点を決める

起点は、この変更要求が直接変える文書である。`changes` に書く。

- 依頼の内容と、バンドルの文書の本文を読んで、候補を挙げる。候補ごとに、根拠（依頼の文と、文書の該当する箇所）を示す
- 起点は、直接変える文書だけにする。起点から依存関係でたどれる文書（判断、タスク、リスクなど）は、`estimate` が見つけるので、起点に含めない
- 起点の採否は、利用者が決める。選択肢で尋ねる（複数選択）
- 起点に当たる文書がバンドルにない場合（新しい要件など）は、そう伝える。`changes` は書かずに受け付けてよい。その場合、`conflicts` はこの変更要求を比べられないと示す

## 3. 依頼者を特定する

依頼者を、ステークホルダーの文書で特定する。`requested_by` には、その文書のパスを `/` から書く。
`meeting` は、この文書の `side` で、社内の会議と顧客との会議に呼ぶ人を分ける。

- 既存のステークホルダーの文書から、依頼者に当たる文書を探す。表示名（`title`）と組織や部署で照合する。見つかったら、その文書でよいかを確認する
- 見つからなければ、ステークホルダーの文書を作ることを提案する
  - パスは `stakeholders/<id>.md`。`<id>` は、英小文字、数字、`-` で書く
  - フロントマター：`type: Stakeholder`、`title`（組織や部署と、必要なら名前）、`side`（`internal` か `customer`）、`role`（役割）
  - `side` と `role` は、必ず利用者に尋ねる。メールのドメインなどから推測しない
  - 連絡先は書かない。名前と役割だけにする

```yaml
---
type: Stakeholder
title: 顧客B社 経理部
side: customer
role: 発注者の窓口
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---
```

## 4. 変更要求の文書を作る

ここまでの内容で、変更要求の文書の差分を示し、承認を得てから書く。

- パスは `change-requests/<番号>-<内容>.md`。番号は、既存の変更要求にそろえる（`cr-010` まであれば、次は `cr-011`）。`<内容>` は、英小文字、数字、`-` で短く書く
- `type` は、既存の変更要求と同じ名前にする（既定は `Change Request`）
- `state` は、受け付けを表す値にする。既存の変更要求で使っている値にそろえる。なければ `submitted` を勧める

```yaml
---
type: Change Request
title: 月次の報告書をCSVでも出力できるようにする
state: submitted
requested_by: /stakeholders/b-corp.md
received_at: 2026-03-04T09:30:00+09:00
changes: /requirements/req-7-report.md
generated: { by: <エージェント>/<モデルのID>, at: <手順0で取得した日時> }
---

# 月次の報告書をCSVでも出力できるようにする

## 依頼の内容

（依頼の要点。依頼者の言葉をできるだけ残す）

## 受け付けの記録

- 受け付けた経路：メール（件名「…」）
```

- 本文には、依頼の要点を書く。依頼の文面を引用してもよいが、連絡先と署名は除く
- 影響の見積もりや、ほかの変更要求との判定は、本文に書かない
- `changes` が1件ならスカラー、2件以上ならブロック形式のリストにする
- 新しい文書は、そのディレクトリの `index.md` に、`* [表示名](ファイル名)` の形で1行のリンクを追加する。新しいディレクトリ（`stakeholders/` など）を作ったら、そのディレクトリの `index.md` を作り、ルートの `index.md` にもリンクを追加する
- `log.md` に、受け付けたことを1行追加するかを尋ねる。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Creation**: <説明>` の形で、新しい順に書く。説明は、バンドルの文書と同じ言葉で書く

書いた後に `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す。

## 5. 影響を見積もる

起点（`changes`）がない変更要求には、`estimate` を実行しない。`estimate` はエラーになる。その場合は、起点がないので影響範囲を示せないと報告し、手順6に進む。

1. `adaptrace estimate --request <変更要求>` を実行する。`changes` の文書を起点に、届く文書、型ごとの数、関わる人、期日に響くマイルストーン、作り直しになる終わったタスクが示される
2. 起点と、届く文書の本文を読み、文書ごとに次を判断する
   - 見直しが必要か（要る、たぶん要る、たぶん要らない）と、その理由
   - 必要な場合の規模（小、中、大）と、工数の目安（人時）
3. 見積もりの前提を、表にする前に利用者に確認する
   - 前提は、見積もりを左右するのに、依頼にも文書にも決まったこととして書かれていないこと。たとえば、どの仕組みや事業者を使うか、どこまでを今回の範囲にするか
   - 文書から読み取れる「できること」（「使っているサービスが、その機能も持っている」など）は、「そうすると決まったこと」ではない。前提として示し、確認を取る
   - 前提ごとに、推測した内容と根拠を示し、「この前提で見積もってよいか」を尋ねる。利用者が決めていなければ、前提が変わると工数が変わる箇所を、見積もりに書く
4. 結果を表にまとめる。合計の工数と、確認した前提、まだ決まっていない前提も書く

| 文書 | 見直し | 規模 | 工数の目安 | 理由 |
|---|---|---|---|---|
| `requirements/req-7-report.md` | 要る | 小 | 1人時 | 出力の形式にCSVを追加する |

- 見積もりは、このエージェントの判断である。報告では、判断の材料であって、確定した見積もりではないと書く
- `--llm` は使わない。必要な判断は、このエージェントが行う

## 6. 重なる変更要求を確認する

1. `adaptrace conflicts --format json` を実行し、今回の変更要求を含む組を取り出す。`state` が決着した値（`approved`、`rejected` など）の変更要求は、対象にならない
2. 組ごとに、2つの変更要求の本文と、両方が変える文書の本文を読み、次の4つのどれかに判定する
   - `conflict`：両立できない
   - `duplicate`：同じことを求めている（別の言葉や、別の人からでも）
   - `compatible`：両立できる
   - `unclear`：文書だけでは判断できない
3. 組ごとに、理由と、協議で決めるべき点を書く
4. 結果を表にまとめる。1つの組を1行にし、判定の列には4つの値のどれか1つだけを書く

| 組 | 判定 | 理由 | 協議で決めるべき点 |
|---|---|---|---|
| `cr-009` と `cr-011` | conflict | `cr-009` は報告書をPDFだけにし、`cr-011` はCSVを追加する | どちらを優先するか |

- 重なる組がなければ、そう伝える
- 起点がない変更要求は、重なりを確認できない。そう報告する。`conflicts` は、型が `Change Request` の文書だけを、比べられない変更要求（JSONの `unlinked`）として示す。型の名前が違うと、`unlinked` にも出ないので、「重なりがない」と誤って報告しない
- 判定は、協議の材料であって、決定ではない

## 7. 報告する

次をまとめて報告する。報告は会話の中で行い、ファイルには書かない。

- 作った文書（変更要求、ステークホルダー）と、`validate` の結果
- 起点と、影響範囲の見積もり（手順5の表と合計）
- 重なる変更要求と、判定、協議で決めるべき点（手順6）
- 利用者が後で決めること（承認するか、誰と協議するかなど）

重なる組があれば、協議の会議を準備するかを尋ねる。準備する場合：

1. まず社内の会議にする：`adaptrace meeting <今回の変更要求> <重なる変更要求>... --audience internal`
2. 示された参加者の候補、議題、`Meeting` の下書きを利用者に見せる。「招待の前に確認が必要」と示された人がいれば、伝える
3. 下書きをファイルにするかを尋ね、承認されたら `--write` を付けて実行する。「ファイルにする」とはっきり答えたときだけを承認とする。「おすすめで」「任せる」と答えたときは、おすすめと理由を示して、もう一度尋ねる
4. `--write` は、`Meeting` の下書きのファイルだけを作る。続けて、次を差分で示し、承認を得てから書く
   - 下書きを置いたディレクトリ（既定は `meetings/`）の `index.md` に、下書きへのリンクを追加する。ディレクトリが新しければ、そのディレクトリの `index.md` を作り、ルートの `index.md` にもリンクを追加する
   - `log.md` に、会議の下書きを作ったことを記録するかを尋ねる
   - 追加したら、`adaptrace validate` を実行する
5. 日程調整と招待の送信はしない。それは人が行う
