# adaptrace-change-decision

変更要求の判断（承認、却下、保留）を、バンドル（既定は `.adaptrace/`）の変更要求の文書に記録する。
1回の作業で、複数の変更要求の判断を記録できる。
承認した変更要求の見直し（起点への `derived_from` の追加から、反映済みにするまで）は、このskillでは行わない。skill `adaptrace-review` で進める。
手順は、Adaptraceのガイド「PMBOKの文書を変更要求に合わせて更新する」（`docs/guide/pmbok.md`）の「3. 変更要求を受け付ける」と「4. 承認されたら、上流から順に更新する」の間に当たる。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、差分を示して承認を得る（Adaptraceの設計原則6）
- 差分は、文書ごとに示す。複数の文書の差分をまとめて示し、1回で承認を得てもよい。その場合も、どの文書を書くかを一覧にして確認する
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる。差分には選択肢を含めず、決まった内容だけを書く
- **変更要求を、自分で承認、却下、保留にしない。** 記録するのは、利用者が伝えた判断だけにする。判断が伝えられていない変更要求は、変更しない
- **判断の理由、日付、判断した人を、推測で書かない。** 分からなければ尋ねる。利用者が分からないと答えたら、その項目を書かずに、後で書くよう伝える。否定（「条件はない」など）は書かない。確認の質問に利用者が「ない」と答えた項目も書かない
- 変更要求の文書で変えるのは、`state`、`generated`、本文の末尾に追加する「判断」の見出しだけにする。`received_at`、`changes`、`requested_by`、受け付けたときの本文は変えない
- ほかの文書（要件、判断、タスク、ほかの変更要求、`index.md` など）は変更しない。新しい文書も作らない。起点への `derived_from` の追加は、skill `adaptrace-review` が行う。変更が必要だと思ったら、報告に書く（`index.md` に変更要求の状態を書いている場合など）
- 依頼者への連絡は、人が行う。利用者が望めば、連絡の文案を会話の中で示す。文案は、バンドルに書かない
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace progress change-requests/cr-011-csv-export.md` |
| 本文のリンク | その文書からの相対パス | `[11月26日の変更管理の会議](../meetings/2026-11-26.md)` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。なければ、利用者に尋ねる。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける
3. 今の状態を調べる
   - `adaptrace validate`：判断の記録の前からあるエラーと警告を把握しておく
   - `adaptrace list --format json --columns type,state`：文書の一覧。変更要求と議事録の型の名前（`Change Request`、`Meeting` など）を、ここで確認する。`list` は `status: deprecated` の文書を含めない
   - `adaptrace list --type "<変更要求の型>" --format json --columns state,requested_by,received_at,changes`：変更要求の一覧
4. 今の日時を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）。今回更新する文書の `generated.at` には、すべてこの値を使う

## 1. 判断の内容を確認する

1. 判断を記録する変更要求を特定する。利用者が番号や題で言ったときは、手順0の一覧からパスを確認する。見つからなければ、推測せずに尋ねる
2. 変更要求の本文を読む
3. 変更要求ごとに、次を確認する。利用者の依頼に書いてあれば、尋ねずに使う。足りない項目だけを、まとめて尋ねる。手順2の `state` の値と、手順4の `generated.by` のIDも、分からなければ同じ質問にまとめてよい
   - 結果：承認、却下、保留のどれか。条件付きの承認なら、その条件
   - 判断した日。年が省かれていれば、今日の日付の年で補う。補った日が今日より後になるときは、前年にする。補ったことを利用者に伝えて、確認を得る
   - 判断した会議の名前か、判断した人。利用者が挙げた人（議長など）は書いてよい。人は、利用者が呼んだ名前で書く。会議の呼び方は、既存の「判断」の見出しにそろえる
   - 理由
   - 保留なら、再検討の時期か条件
4. 判断した会議の議事録が、バンドルにあるかを確認する。手順0の一覧で、議事録の型（`Meeting` など）の文書を探し、日付と題で照合する。議事録の型がないか、該当する文書が見つからなければ、議事録へのリンクは書かない。議事録を新しく作ることは、このskillでは行わない
5. `state` がすでに決着を表す値（承認、却下など）の変更要求は、判断を変えるのかを確認する。変える場合も、前の「判断」の見出しは消さず、新しい「判断」の見出しを下に追加する

## 2. `state` の値を決める

`state` の値の一覧は、プロジェクトごとに決める。値を定める設定ファイルはない。このskillでも値を固定しない。

1. 手順0の一覧で、既存の変更要求が使っている `state` の値を確認する。それぞれの値が、決着（承認、却下、保留、反映済みなど）を表すか、未決（受付、検討中など）を表すかを分ける。名前から分からない値は、利用者に尋ねる
2. 判断ごとに、使う値を決める
   - 既存の値に、承認、却下、保留を表す値があれば、それを使う（例：却下に `declined` を使っていれば、`rejected` にしない）
   - 該当する値がなければ、`approved`（承認）、`rejected`（却下）、`deferred`（保留）を勧め、利用者の確認を得る。`conflicts` が決着とみなす既定の値だからである。利用者が既存に合わせるよう求めていて、該当する値がない場合も、この3つを勧めて確認を得る。既存の値と、勧めた値が混ざってもよい
3. 値が決まってから、`conflicts` に渡す決着の値の一覧を決める。`conflicts` の既定の値は、`approved`、`accepted`、`rejected`、`deferred`、`implemented`、`closed`、`done`。既存の変更要求が使っている決着の値と、今回決めた値に、既定にない値が1つでもあれば、手順3と手順6で `conflicts` に `--settled <値,...>` を付ける。`--settled` は既定の値を置き換えるので、既定の値、既存の決着の値、今回決めた値をすべて並べる

## 3. 書く前に、重なりと見直しの状況を調べる

**どの文書を書くよりも前に**、次を実行する。判断を記録した変更要求は決着した値になり、`conflicts` の対象から外れるため。

1. `adaptrace conflicts --format json`（手順2の3で決めた `--settled` を付ける）：`pairs` から、今回判断する変更要求を含む組を取り出す。組の各要素は、`a`、`b`、`sharedTargets`（両方が `changes` で指す起点）、`overlap`（両方の影響範囲に入る文書）。相手が今回判断しない変更要求なら、その相手は判断の後も未決のまま残る。組と、`sharedTargets` と `overlap` を控えておく
   - すでに決着した値の変更要求を判断し直す場合は、その変更要求の今の値を除いた `--settled` で、もう一度 `conflicts` を実行する。決着した値のままでは、`conflicts` の対象にならないため。その結果からは、判断し直す変更要求を含む組だけを使う
2. `adaptrace graph --format json` の `backlinks` で、変更要求ごとに、そのパスのキーを見る。`kind` が `derived_from` の項目があれば、どの文書からでも当てはまる。あれば、見直しがすでに始まっている。その変更要求は、手順4で本文と `generated` を変えない
3. 承認する変更要求ごとに、`changes` があるかを確認する。`changes` がなければ起点がなく、`adaptrace-review` で見直しを始められないので、報告に書く。`changes` が指す文書がないときは、手順0の `validate` がエラーとして示している。`changes` の値は先頭に `/` が付く。コマンドに渡すときは、先頭の `/` を外す

## 4. 変更要求の文書を更新する

変更要求ごとに、差分を示し、承認を得てから書く。差分は、変える行（`state`、`generated`）と、追加する「判断」の見出しを示す。変えない本文は省いてよい。

- `state` を、手順2で決めた値にする
- 本文の末尾に「判断」の見出しを追加する。見出しは、本文の言語で書く（英語の本文なら `Decision`）。手順1で確認した内容だけを書く。分からない項目は書かない
  - 1文目に、いつ、誰が、どう判断したかを書く
  - 理由を書く。条件付きの承認なら条件を、保留なら再検討の時期か条件を書く
  - 会議の議事録の文書があれば、本文から相対パスでリンクする。`derived_from` などの依存関係にはしない
- `generated` を、手順0で取得した日時にする。`by` は、このskillで判断を記録するよう依頼した利用者にする（`human:<ID>`）。議長など、判断した人が別にいても、依頼した利用者にする。判断の記録は、利用者が伝えた判断を書いたものだからである。IDの書き方は、既存の文書にそろえる。分からなければ尋ねる。受け付けたときの `by` は上書きしてよい。受け付けた日時は `received_at` に残る
- 手順3の2で、すでに変更要求を `derived_from` で指す文書があった変更要求は、`state` だけを変える。本文と `generated` は変えない。変更要求の `generated` を新しくすると、見直した起点が古いと示されるため。判断の内容は、手順5の `log.md` に書く
- `received_at`、`changes`、`requested_by`、ほかのキー、受け付けたときの本文は変えない

```markdown
---
type: Change Request
title: 検索結果をCSVで出力できるようにする
state: approved
requested_by: /stakeholders/sales.md
received_at: 2026-11-10T09:30:00+09:00
changes: /requirements/req-7-report.md
generated: { by: human:sato, at: <手順0で取得した日時> }   # 記録を依頼した利用者
---

# 検索結果をCSVで出力できるようにする

（受け付けたときの本文。変えない）

## 判断

2026-11-26の変更管理の会議（議長：田中）で、承認した。営業部門からの要望が多く、出力の機能は既存の帳票の仕組みで作れるため。
```

## 5. 記録する

1. `log.md` に記録するかを尋ねる。手順4の差分と一緒に尋ねてよい。手順4で本文を変えなかった変更要求があれば、`log.md` が判断の唯一の記録になることを伝えてから尋ねる
2. 追加する場合は、今日（作業した日）の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Update**: <説明>` の形で1行書く。説明には、判断した会議と日、変更要求ごとの判断を書く。番号の書き方（前後の空白など）は、下の例ではなく、既存の行にそろえる（例：「11月26日の変更管理の会議の判断を記録した。cr-011 を承認、cr-012 を却下」）。手順4で本文を変えなかった変更要求は、判断の理由もここに書く
3. `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す。修正の承認を待つ間、書いた内容は戻さない。`validate` は、`state` の値や「判断」の見出しの内容は検査しない。それらは、手順4の差分で確認したとおりである

## 6. 報告する

次をまとめて報告する。報告は会話の中で行い、ファイルには書かない。

- 変更要求ごとの判断と、書いた `state` の値
- 承認した変更要求
  - 見直しは、skill `adaptrace-review` で進められる。起点（`changes` が指す文書）への `derived_from` の追加から始まる
  - 見直す順番の目安として、起点ごとに `adaptrace impact <起点> --order review` の順番の一覧を示してよい。一覧には起点自身は含まれず、起点の次に見直す文書から始まる。この時点では、最後の行が「0 documents to review」になる。起点がまだ更新されていないためで、見直しが要らないという意味ではない。この行は示さない
  - `changes` がない変更要求は、見直しを始める前に起点を決める必要がある
- 手順3の1で控えた、判断の後も未決のまま残る変更要求。今回判断した複数の変更要求と重なっていれば、それぞれについて報告する
  - 承認した変更要求と重なっていた場合：重なる文書が承認によって変わるので、その変更要求の見積もりと判定をやり直す必要がある
  - 却下した変更要求と重なっていた場合：その重なりは、もう考えなくてよい
  - 保留にした変更要求と重なっていた場合：今は重なりの対象から外れるが、保留にした変更要求を再検討するときに、もう一度重なりを確認する
- 今回判断した変更要求どうしの組：承認した変更要求と、保留にした変更要求が重なっていれば、保留にした変更要求を再検討するときには、起点がすでに変わっていることを報告する。却下した変更要求との組は、報告しなくてよい
- 却下や保留にした変更要求の依頼者（`requested_by`）への連絡は、人が行う。利用者が望めば、連絡の文案を会話の中で示す
- 手順0の時点より増えた `validate` のエラーと警告
