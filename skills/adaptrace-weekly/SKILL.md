# adaptrace-weekly

定例の会議の前に、バンドル（既定は `.adaptrace/`）の状況をまとめ、議題の案を示す。
手順は、Adaptraceのガイド「プロジェクトマネジメントでの使い方」（`docs/guide/project-management.md`）の「定例の点検」に従う。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **文書を変更しない。** 見つかった問題は議題として示し、修正の方法（次に使うskillやコマンド）を案内する。修正は、利用者が別に行う
- 書き込むのは、議事録の下書き（`type: Meeting` の文書）と、それを指す `index.md` と `log.md` だけ。どれも、差分を示して承認を得てから書く
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- タスクが遅れている理由や、担当者の状況を推測で書かない。文書に書いてあることだけを示す
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける
3. 今日の日付を取得する。バンドルの日時と同じタイムゾーンで決める（例：日時が `+09:00` なら、GNUのdateで `date --date='TZ="Asia/Tokyo" now' +%F`）。タイムゾーンが違うと、期日の判断が1日ずれる
4. 次の定例の日を尋ね、返事を待ってから手順1に進む。利用者が分からないと答えたら、今日から7日後にする。この日までを「次の定例まで」と呼ぶ

## 1. 状況を集める

次のコマンドを実行する。どれも書き込まない。

| 調べること | コマンド |
|---|---|
| 壊れた依存先、循環、デッドロック、日時の警告 | `adaptrace validate --format json` |
| 依存先より古い文書、見直し時期（`stale_after`）を過ぎた文書 | `adaptrace stale --format json` |
| タスクの `state` ごとの一覧と、待っているタスク | `adaptrace board --format json` |
| タスクとマイルストーンの期日 | `adaptrace list --type Task --columns state,owner,due --format json`、`adaptrace list --type Milestone --columns state,due --format json` |
| 変更要求の状況 | `adaptrace list --type "Change Request" --columns state,received_at --format json` |
| 見直し中の変更要求の進み具合 | 承認済みで、反映済みでない変更要求ごとに `adaptrace progress <変更要求>` |
| 重なる未決の変更要求 | `adaptrace conflicts --format json` |

- 型の名前は、バンドルで使っている名前にそろえる。`Milestone` や `Change Request` の文書がなければ、その行は飛ばす
- 終わったタスクは、期日の判断から除く。終わりを表す `state` は、`board` の列の名前から判断する（`done`、`closed`、`completed` など）。迷ったら利用者に尋ねる。`state` のないマイルストーンは、終わっていないものとして扱う
- 変更要求の `state` は、既存の変更要求で使っている値から判断する。目安は、承認済みが `approved` と `accepted`、反映済みが `implemented`、`closed`、`done`、未決がそれ以外（`submitted` など）、決着して見直しが要らないものが `rejected` と `deferred`
- `stale --format json` の理由（`reasons[].kind`）は、次の区分に分ける。`older-than-dependency`、`resource-changed`、`resource-unrecorded`、`resource-missing` は「見直しが必要な文書」、`expired` は「見直し時期を過ぎた文書」。`unknown` の文書（最終更新が分からない）は、「バンドルの問題」に入れる
- `conflicts --format json` で議題にするのは `pairs`（重なる組）だけ。`unlinked`（起点のない変更要求）は「バンドルの問題」に入れる
- `progress` は、見直しが終わるまで終了コード1を返す。途中の1は正常である

## 2. 議題の案をまとめる

集めた結果を、次の区分で表にまとめる。区分ごとに、該当がなければ「なし」と書く。

| 区分 | 示すもの | 次の一手 |
|---|---|---|
| 期限を過ぎたもの | 期日が今日より前で、終わっていないタスクとマイルストーン | 担当者に状況を確認する |
| 次の定例までに期限が来るもの | 期日が今日から次の定例までのタスクとマイルストーン | 担当者に見通しを確認する |
| 待っているタスク | `board` の `waitingFor` があるタスクと、その相手 | 待ちの相手を先に進める |
| 見直しが必要な文書 | `stale` の古い文書（依存先より古い、ファイルが変わった） | skill `adaptrace-review`、または `adaptrace impact <依存先> --order review` |
| 見直し時期を過ぎた文書 | `stale` の `stale_after` を過ぎた文書（リスクなど） | 内容を見直し、変えたら `generated` を、変えなければ `verified` を更新する。あわせて `stale_after` を次の見直しの日に進める。進めないと、次の定例でも期限切れとして示される |
| 見直し中の変更要求 | 承認済みで反映済みでない変更要求と、`progress` の見直し済みの数 | skill `adaptrace-review` で続ける |
| 未決の変更要求 | 受け付けたが決着していない変更要求と、受け付けた日 | 判断の場を決める。重なりがあれば `adaptrace meeting` |
| 重なる変更要求 | `conflicts` の組 | 協議の会議を準備する（`adaptrace meeting`） |
| バンドルの問題 | `validate` のエラーと警告（`missing-generated`、`stale-generated` など） | 警告の内容に従って修正する |

- 各行に、文書のパスと表示名、担当（`owner`）があれば担当を書く
- 期日は、今日から何日後か（何日過ぎたか）も書く
- 順番は、上の表の順にする。期限を過ぎたものを先に示す

## 3. 報告する

1. 議題の案を、会話の中で示す。最初に、区分ごとの件数を1行でまとめる
2. 議事録の下書きを作るかを尋ねる

議事録の下書きを作る場合：

- パスは `meetings/<次の定例の日>-weekly.md`。同じパスがあれば、`-2`、`-3` を付ける
- フロントマター

```yaml
---
type: Meeting
title: 定例2026-12-03
status: draft
generated: { by: <エージェント>/<モデルのID>, at: <書き込む日時> }
---
```

- 本文は、議題の案の表と、「決まったこと」「宿題」の空の見出しにする。文書へのリンクは、`../tasks/login-mfa.md` のような相対パスで書く。依存関係のキーは付けない。議題の文書が変わっても、議事録を見直す必要はないため
- `meetings/index.md` に、`* [表示名](ファイル名)` の形で1行のリンクを追加する。`meetings/` がなければ、`meetings/index.md` を作り、ルートの `index.md` にもリンクを追加する
- `log.md` に記録するかを尋ねる。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Creation**: <説明>` の形で、新しい順に書く
- 差分を示し、承認を得てから書く。書いた後に `adaptrace validate` を実行する
