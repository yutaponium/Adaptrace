# adaptrace-milestone

マイルストーンの前に、バンドル（既定は `.adaptrace/`）から、達成できるかを判断する材料をまとめる。
残っている事柄ごとに、扱いを利用者と決め、マイルストーンの計画（範囲と期日）を更新する。
達成できるかの判断は人が行う。このskillは、材料と選択肢を示す。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。`coverage` の判定の規則も、そこにある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、差分を示して承認を得る（Adaptraceの設計原則6）
- 差分は、文書ごとに示す。複数の文書の差分をまとめて示し、1回で承認を得てもよい。その場合も、どの文書を書くかを一覧にして確認する
- 利用者が「おすすめで」と判断を任せても、それは書き込みの承認ではない。おすすめの内容を差分で示し、書き込んでよいかを改めて尋ねる
- **達成できるかを、自分で判定しない。** 材料と、項目ごとの選択肢を示す。判断は利用者が行う
- 書き換えてよいのは、次のキーと `log.md` だけにする。ほかの文書とキーは変えない。新しい文書も作らない
  - マイルストーンの文書：`due`、`depends_on`、`blocks`、`state`
  - 作業（Task）の文書：`due`、`blocks`
  - `log.md`：行を追加するだけ
- 要件、判断、変更要求の文書は変えない。要件の内容や範囲を変える必要があれば、変更要求として受け付けるよう案内する（skill `adaptrace-change-request`）
- 作業が足りない要件に、タスクを作らない。足りないことを報告し、作るかどうかは利用者が決める
- 依存関係のキー、`due`、`state` だけを変えるときは、`generated` を変えない
- コミットとpushは、利用者に頼まれたときだけ行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace coverage --milestone milestones/release-1.md` |
| フロントマターのキーの値 | バンドルの中のパス。先頭に `/` を付ける | `depends_on: /tasks/login-mfa.md` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/`。なければ、利用者に尋ねる。ほかの場所にあれば、以降のすべてのコマンドに `--bundle <ディレクトリ>` を付ける
3. `adaptrace validate` を実行し、判定の前からあるエラーと警告を把握しておく
4. 今の日付を、タイムゾーン付きで1回だけ取得する（例：GNUのdateなら `date --iso-8601=seconds`）。期日を過ぎたかの判断と、`log.md` の見出しに使う

## 1. マイルストーンを確認する

1. `adaptrace list --format json --columns type,state`：文書の一覧。型の名前（`Milestone`、`Task`、`Change Request` など）と、型ごとに使っている `state` の値を、ここで確認する。`state` が空文字（`""`）の文書は、`state` を持たない
2. `adaptrace list --type Milestone --format json --columns state,due`：マイルストーンの一覧
3. 利用者が名前や番号で言ったマイルストーンを、一覧から特定する。見つからなければ、推測せずに尋ねる
4. マイルストーンの本文を読む。期日（`due`）と、`state` を確認する。`state` がなければ、まだ終わっていない
5. 手順1の1で確認した、TaskとMilestoneの `state` の値のうち、終わったことを表す値を決める。`coverage` の既定は `done` である。`done` 以外に、終わったことを表すと名前から分かる値（`completed` など）があれば、以降の `coverage` に `--done <値,...>` を付ける。`--done` は既定を置き換えるので、`done` も使っていれば一緒に並べる（例：`--done done,completed`）。どちらか分からない値があれば、利用者に尋ねる
6. 手順1の1で確認した、変更要求の `state` の値を、未決（受付、検討中など）と決着（承認、却下など）に分ける。手順2の2で使う。名前から分からない値は、利用者に尋ねる

## 2. 材料を集める

1. `adaptrace coverage --milestone <マイルストーン> --format json`
   - `requirements`：範囲の要件と状況（`uncovered`、`open`、`covered`）。要件は、マイルストーンが直接待っている要件と、範囲の作業が `satisfies` で満たす要件である。`satisfiers` の `counted` が `false` の文書は、別のリリースの作業として数えていない。Decisionなど作業でない文書は、`done` が `null` で、あれば満たしているとみなす
   - `scope`：範囲の文書。マイルストーンが待っている文書と、そこから待っている文書をたどった文書、要件を満たす作業が入る。作業が依存する判断なども入るが、その先はたどらない。`done` が `false` のTaskとMilestoneが、残っている作業。`done` が `null` の文書（要件や判断）は、作業ではないので、作業の一覧には入れない。`late` が `true` の作業は、終わっておらず、期日がマイルストーンより後
2. `adaptrace conflicts --format json`：`requests` から、未決の変更要求を取り出す。`reach`（影響範囲）が、`coverage` の `scope` か `requirements` の文書か、マイルストーン自身と1つでも重なる変更要求が、このマイルストーンに関わる。`changes` を持たない変更要求（`unlinked`）は、関わるかを判断できないので、報告に書く。`pairs`（変更要求どうしの重なり）は、このskillでは使わない
   - `conflicts` に渡す決着の値の一覧を決める。既定は `approved`、`accepted`、`rejected`、`deferred`、`implemented`、`closed`、`done`。一覧は、既定から、手順1の6で未決に分けた値（`deferred` を「保留中で未決」として使っている場合など）を除き、決着に分けた値を加えたものにする。一覧が既定と違えば、`--settled` を付ける。`--settled` は既定を置き換えるので、一覧のすべての値を並べる
3. `adaptrace stale --format json`：`stale` のうち、マイルストーン自身と、`scope` か `requirements` にある文書。`unknown`（日時が分からない文書）のうち範囲にあるものも、報告に書く
4. `scope` の作業のうち、手順0の日付より前の期日で、終わっていないものを、期日を過ぎた作業として控える。日付は、`due` の日付と、手順0の日時の日付部分で比べる

## 3. 材料を示す

次の表で示す。おすすめの判断は書かない。項目がない区分は「なし」と書く。

| 区分 | 項目 | 内容 |
|---|---|---|
| 作業が足りない要件（`uncovered`） | 要件 | 満たす作業がない |
| 終わっていない要件（`open`） | 要件と、終わっていない作業 | 作業の担当と期日 |
| 期日に間に合わない作業（`late`、期日を過ぎた作業） | 作業 | 期日と担当 |
| そのほかの残っている作業 | 作業（`scope` の `done` が `false` のTaskとMilestoneで、上の区分にないもの） | 状態、担当、期日 |
| 範囲に関わる未決の変更要求 | 変更要求 | 重なる文書 |
| 古くなった文書 | 文書 | 何より古いか |

作業の担当と期日は、`scope` の `owner` と `due` から取る。`scope` にない作業（`counted` が `false` のもの）は、その文書を読む。1つの作業が複数の区分に入るときは、それぞれの区分に示す。件数は、区分ごとに示す。マイルストーンの期日までの日数は、期日の日付から今日の日付を引いた日数にする。

そのうえで、項目ごとに扱いを決めるかを尋ねる。利用者が判断だけを求めたら、手順4と手順5を飛ばして、手順6で報告する。その場合は、変えた文書はないと書く。

## 4. 項目ごとに扱いを決める

項目ごとに、次の選択肢を示して尋ねる。本文を読んで、おすすめと理由を添えてよい。似た項目は、まとめて尋ねてよい。

| 扱い | 向いている場合 | 変更 |
|---|---|---|
| そのままにする | 期日までに終わる見込みがある。リスクとして受け入れる。作業が足りない要件なら、利用者がタスクを作る予定である | 変更しない |
| 作業を別のマイルストーンに移す | このリリースでは終わらない | マイルストーンの `depends_on` で待っていた作業なら、このマイルストーンの `depends_on` から外し、移す先のマイルストーンの `depends_on` に追加する。作業の `blocks` でこのマイルストーンを指していた作業なら、`blocks` の値を移す先のマイルストーンに付け替える。元の書き方にそろえるためである |
| 期日を変える | 作業か、マイルストーンの期日を動かせる | 作業かマイルストーンの `due` を変える |
| 要件を範囲から外す | このリリースで満たさないと決めた | マイルストーンが要件を直接 `depends_on` で指していれば、外す。範囲の作業が `satisfies` で満たしているので示す要件は、その作業が範囲にある限り外れない。外すには、その作業を移す。顧客と合意した要件なら、外す前に変更要求として受け付けるよう案内する（skill `adaptrace-change-request`） |
| 変更要求を先に判断する | 範囲に関わる未決の変更要求がある | 変更しない。skill `adaptrace-change-decision` を案内する |

- 移す先のマイルストーンは、手順1の一覧から利用者に選んでもらう。なければ、新しく作らずに、そのことを報告に書く。移す先の `due` と、作業の `due` を照らし、移した先でも期日に間に合わないなら、そのことを伝える
- 移す作業は、マイルストーンが `depends_on` で直接待っているか、作業の `blocks` がマイルストーンを指しているものに限る。移す前に、`adaptrace graph --format json` の `edges` で、範囲のほかの作業がその作業を待っていないか（`depends_on` か `blocks`）を確認する。待っていれば、直接の依存を外しても範囲に残るので、そのことを伝えて扱いを尋ねる。ほかの作業を通じて待っている作業は、このskillでは移さない。どの作業を通じて待っているかを `adaptrace graph --format json` の `edges` で示し、扱いを利用者に任せる
- **要件を満たす作業（`satisfies`）を移すときは、利用者に確認する。** 移した作業は、このマイルストーンの要件の判定に数えなくなる。残りの作業が終われば、要件は `covered` と示されるが、要件の一部はこのリリースで満たさないことになる。要件の範囲を顧客と合意し直す必要があれば、変更要求として受け付けるよう案内する（skill `adaptrace-change-request`）。マイルストーンが要件を直接待っている場合は、移した作業も数え続けるので、要件は `open` のままになる
- 作業が足りない要件（`uncovered`）に、タスクを作らない。足りないことを報告に書く
- 変更要求の判断や、要件の変更は、このskillでは行わない

## 5. 書く

1. 手順4で決めた変更を、文書ごとに差分で示し、承認を得てから書く
   - 変えるのは、決めたキーだけにする。`generated` は変えない
   - `depends_on` の値が1つになっても、既存の書き方（リスト）にそろえる。空になれば、キーごと削除する。追加する値は、リストの末尾に置く
2. 項目がすべて片付き、範囲の作業が終わっていると利用者が判断したら、マイルストーンの `state` を終わった値にするかを尋ねる。値は、手順1の5で決めた値にそろえる。決めた値がなければ尋ねる
3. `log.md` に記録するかを尋ねる。この手順の1の差分と一緒に尋ねてよい。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、`* **Update**: <説明>` の形で、この作業全体を1行で書く。説明には、マイルストーンと、変えた扱いを書く
4. `adaptrace validate` を実行する。手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す
5. `adaptrace coverage --milestone <マイルストーン> --format json` をもう一度実行し、変更の後の状況を確認する。移した作業が、このマイルストーンの `scope` から外れたことを確認する。外れていなければ、残っている経路を報告する。作業を移した先のマイルストーンでも実行し、移した作業が範囲に入ったことを確認する

## 6. 報告する

次をまとめて報告する。報告は会話の中で行い、ファイルには書かない。

- マイルストーンと期日。変更後の、要件の状況ごとの件数
- 項目ごとに決めた扱いと、変えた文書
- 残っているリスク：そのままにした作業、作業が足りない要件、期日に間に合わない作業、満たす作業の一部を移した要件
- 人が行うこと：未決の変更要求の判断（skill `adaptrace-change-decision`）、要件の変更（skill `adaptrace-change-request`）、足りない作業のタスクの作成
- マイルストーン自身が満たす要件（`satisfies`）は、マイルストーンの `state` を終わった値にするまで `open` と示されることを、該当すれば伝える
- 手順0の時点より増えた `validate` のエラーと警告
