# adaptrace-adopt

指定されたファイルを、Adaptraceのバンドル（既定は `.adaptrace/`）に取り込み、依存関係を張る。
手順は、Adaptraceのガイド「既存のリポジトリにAdaptraceを導入する」（`docs/guide/adoption.md`）の手順4と5に従う。
キーとコマンドの正確な決まりは、Adaptraceの `docs/spec/schema.md` にある。
どれもAdaptraceのリポジトリにあり、探し方は下の「共通の書き方」にある。手順の判断に迷ったときに読む。

## 守ること

- **利用者が承認する前に、ファイルを書き換えない。** 書き込む前に、ファイルごとに差分を示して承認を得る。承認されなかった変更は書かない（Adaptraceの設計原則6）
- 担当者（`owner`）、日時、`state` を推測で埋めない。文書に書いてなければ、利用者に尋ねる。分からなければ書かない
- 指定されたファイルと、承認された依存関係の相手の文書だけを変更する。ほかのファイルを変えたくなったら、先に尋ねる
- 連絡先（メールアドレス、電話番号）や秘密情報は、フロントマターに書かない
- コミットとpushは、利用者に頼まれたときだけ行う
- 手順1から4では、計画を立てるだけで、ファイルを変えない（手順0の `init` を除く）。書き込みは、手順5でまとめて行う
- 利用者に尋ねるときは、選択肢で尋ねるツール（AskUserQuestion）があれば使う。なければ、番号付きの選択肢を文章で示して、返事を待つ
- 利用者が「おすすめで」と判断を任せたら、おすすめの値とその理由を差分の中で示し、承認を得る

## パスの書き方

| 場面 | 書き方 | 例 |
|---|---|---|
| コマンドに渡す文書 | バンドルの中のパス。先頭に `/` を付けない | `adaptrace impact requirements/req-1-mfa.md` |
| 依存関係のキーの値 | バンドルの中のパス。先頭に `/` を付ける | `satisfies: /requirements/req-1-mfa.md` |
| `resource` の値 | 代わりの文書からの相対パス。`./` か `../` から書く | `resource: ../../pm/schedule.xlsx` |

## 共通の書き方

Adaptraceのskillに共通の決まり。

- **コマンドの書き方**：手順0で決めた実行方法を、このskillでは `adaptrace` と書く。実行するときは、`adaptrace` をそのコマンドに置き換え、毎回省略せずに書く（例：`bun ~/tools/adaptrace/src/cli.ts validate`）。1回に1つのコマンドを実行する。シェルの変数、エイリアス、ループ、`&&` や `;` でのつなぎ、`$?` を使わない。実行環境によっては、拒否されたり承認を求められたりするため。終了コードは、コマンドが失敗したときにツールの結果に示される。ファイルを読むときは、シェルではなく、ファイルを読むツール（Readなど）を使う。コマンドは、作業中のリポジトリのルートで実行する。バンドルの既定の場所と、コマンドに渡すパスは、ルートを基準にするため
- **Adaptraceの仕様とガイドの場所**：Adaptraceのリポジトリにあり、作業中のリポジトリにはない。次の順に探す
  1. 実行方法が `bun <パス>/src/cli.ts` なら、仕様は `<パス>/docs/spec/schema.md`、ガイドは `<パス>/docs/guide/` にある
  2. `bun add -g` でインストールした `adaptrace` コマンドなら、Bunの既定では `~/.bun/install/global/node_modules/adaptrace/docs/` にある
  3. このskillをClaude Codeのプラグインとしてインストールした場合は、`${CLAUDE_PLUGIN_ROOT}/docs/` にある（仕様は `spec/schema.md`、ガイドは `guide/`）
  4. どれもないか、読めなければ、`adaptrace --version` で版を確かめ、 `https://github.com/yutaponium/Adaptrace/tree/v<版>/docs` を読む。それも読めなければ、推測せずに利用者に尋ねる
  - 型、キー、`state` の値の決まりに迷ったら、文書を書く前に仕様を読む
- **`generated.by`**：skillの手順に `by` の決まりがあれば、それに従う（例：見直しの記録は、判断した人にする）。決まりがなければ、エージェントが書いた文書は `<エージェント>/<モデルのID>` にする（例：`claude-code/claude-opus-5-5`）。モデルのIDは、表示名ではなく、APIで使う識別子である。分からなければ、`<エージェント>` だけにする（例：`claude-code`）。利用者が自分の名前を希望したら、`human:<ID>` にする
- **日時**：`generated.at` などの日時は、タイムゾーン付きのISO 8601で書く（例：`2026-11-26T10:00:00+09:00`）。GNUのdateなら、`date --iso-8601=seconds` で取得できる
- **新しいキーの位置と書き方**：skillの手順に、キーの位置や書き方（1つの値か、リストか）の決まりがあれば、それに従う。決まりがなければ、次のとおりにする。フロントマターのキーの順序に、意味はない。既存の文書の並びにそろえる。手本がなければ、このskillの例の並びに従う。例にないキーは、`generated` の直前に置く。既存の文書がリストで書いていれば、値が1つでもリストにする
- **`log.md`**：日付の見出し（`## YYYY-MM-DD`）は、新しい順に並べる。今日の見出しがなければ、既存の日付の見出しより上に作る。ファイルの題（`# ...`）より上には置かない。行は `* **<ラベル>**: <説明>` の形にする。ラベル（`Creation`、`Update` など）は英語のまま書き、説明はバンドルの文書の本文と同じ言語で書く。`init` が書いた英語の行が既存にあっても、説明は本文の言語でよい。1回の作業は、文書を作ったなら `Creation`、更新したなら `Update` の1行ずつにする。同じ見出しの中では、新しい行を上に書く

## 0. 準備

1. Adaptraceの実行方法を確認する。`adaptrace --version` が動かなければ、利用者に尋ねる（例：`bun ~/tools/adaptrace/src/cli.ts`）。以降、ここで決めたコマンドを `adaptrace` と書く（「共通の書き方」）
2. 作業用のブランチを作るかを尋ねる。取り込みは1つのPRにまとめると、チームで確認しやすい
3. バンドルの場所を確認する。既定は、リポジトリのルートの `.adaptrace/` 。なければ、`adaptrace init --title "<プロジェクト名>"` で作ってよいかを尋ねる。`init` はバンドルの土台だけを作るので、手順5を待たずに実行してよい
4. 今の状態を調べる。バンドルがないと、どちらのコマンドもエラーになるので、`init` の後に実行する
   - `adaptrace validate`：取り込む前からあるエラーを把握しておく。後で、増えたエラーと区別するため
   - `adaptrace list --format json --columns type,state,owner,depends_on,derived_from,satisfies`：既存の文書、型、依存関係。ここに出た文書を、以降「既存の文書」と呼ぶ。新しいバンドルでは、既存の文書はない
5. 型の名前は、バンドルですでに使っている名前にそろえる。PMBOKのテンプレートから作ったバンドルなら、その型の名前を使う
6. コマンドに渡す文書のパスは、バンドルの中のパス（`requirements/mfa.md`）で書く。バンドルの外のパスは受け付けない

## 1. 取り込み方を決める

指定されたファイルごとに、取り込み方を決める。ディレクトリやglobが指定されたら、対象のファイルを列挙して、利用者に確認する。

| ファイル | 取り込み方 |
|---|---|
| バンドルの中にあり、フロントマターがある | そのまま。手順3へ |
| バンドルの中にあり、フロントマターがない | フロントマターを追加する |
| バンドルの外のMarkdown | 「バンドルに移す」か「代わりの文書を置く」かを尋ねる |
| バンドルの外のMarkdown以外（Excel、MS Project、PDFなど） | 代わりの文書を置く |

判断の目安を添えて尋ねる。

- バンドルに移す：これからもMarkdownで更新する文書。移した後は、バンドルの文書が正になる
- 代わりの文書を置く：ほかのツールやWikiが正の文書、ほかの仕組みが読むファイル、Markdown以外のファイル

1つのファイルに、要件や判断が複数書いてある場合は、1件1ファイルに分けることを提案する。依存関係は文書の単位で張るので、分けると影響の範囲を細かく追える。分けるかどうかは、利用者が決める。

議事録やメモに、決まったこと、宿題、リスクが書いてある場合は、それぞれを `Decision`、`Task`、`Risk` の文書として起こすことを提案する。

- 起こした文書は、`derived_from` で議事録を指す
- 宿題の担当者と期日は、議事録に書いてあれば `owner` と `due` に書く
- 利用者がLLMのコマンドを使えるなら、`adaptrace extract <議事録> --llm "<コマンド>"` で下書きを作ってもよい。`extract` は、`--write` を付けなければ書き込まない。ただし、`extract` に渡せるのは、バンドルの中の文書だけ。議事録をまだ取り込んでいなければ、先に議事録の取り込みだけを手順5で書いてから、`extract` を使う
- 議事録そのものは `type: Meeting` の文書として取り込む

起こした文書は、要件や判断とつながることが多い。たとえば、宿題のTaskは要件を `satisfies` で指し、リスクは判断を `depends_on` で指す。依存関係の候補を選ぶとき（手順3）に、忘れずに含める。

## 2. フロントマターを作る

文書ごとに、次のフロントマターを作る。

```yaml
type: Requirement                 # 型。バンドルで使っている名前にそろえる
title: ログインにMFAを入れる       # 本文の見出しや内容から
owner: sato                       # 文書に書いてあるときだけ。なければ尋ねる
generated: { by: human:sato, at: 2026-11-10T10:00:00+09:00 }
```

- `type` は、本文から候補を挙げて、利用者に選んでもらう。PMBOKで使う型の名前（`Schedule Baseline`、`Cost Baseline`、`WBS` など）は、Adaptraceの `examples/pmbok/README.md` にある
- `title` は、元の文書の見出しをそのまま使う。元の文書にID（REQ-1、ADR-0001など）があれば、`title` にも残す
- `state`（進み具合）は、TaskやRiskなど進み具合のある型だけに書く。元の文書に書いてなければ、値を尋ねる
  - バンドルで使っている値があれば、それにそろえる。なければ、Taskは `to_do`、`in_progress`、`done` を勧める。`adaptrace board` が、この値を列として表示するため
  - Riskなどの値は、プロジェクトで決める。候補（`open`、`closed` など）を示して尋ねる
- `owner` は、英字のIDで書くことを勧める。漢字の氏名で書くかは、利用者が決める
- 議事録やメモに書いてある人名は、担当者とは限らない。発言者や起票者のこともある。`owner` にする前に、必ず確認する
- 日付に年や時刻がなければ、文書の文脈（議事録の日付など）から補った値を示して、確認を取る
- `generated.at` は、内容の最終更新の日時をタイムゾーン付きで書く
  - 移す文書と、分けた文書：元のファイルを最後に変えたコミットの日時（`git log -1 --format=%aI -- <元のパス>`）。内容は変わっていないので、取り込みの日時にすると、文書どうしの新旧が失われる。取り込みを始める前から、元のファイルにコミットされていない変更があった場合だけ、今の日時にする
  - 新しく作る文書（代わりの文書、議事録から起こした文書）：今の日時。取り込みの最初に1回だけ取得し、今回新しく作る文書すべてに同じ値を使う。文書ごとに取得すると、依存先の方が数秒新しくなり、`stale` が古いと示すため。取得の例は、GNUのdateなら `date --iso-8601=seconds`。値は `2026-11-25T10:00:00+09:00` の形にする
- `generated.by` は、内容を書いた人や仕組みを表す
  - 移す文書と、分けた文書：内容を書いたのは人なので、元のファイルを最後に変えたコミットの作者（`git log -1 --format=%an -- <元のパス>`）から `human:<id>` を提案し、確認を取る。`<id>` は、英小文字、数字、`-` にする。作者名に空白や日本語が含まれるときや、共有のアカウントのときは、利用者に尋ねる
  - 新しく作る文書：エージェントが作ったことが分かる値にする（「共通の書き方」の `generated.by`）
- `status` には、ライフサイクル（`draft`、`stable`、`deprecated`）だけを書く。進み具合は `state` に書く

### 置き場所とファイル名

- 型ごとのディレクトリに置く（`requirements/`、`decisions/`、`tasks/`、`risks/`、`meetings/`）。`init` が作らない型は、型の名前を小文字にしたディレクトリを作る（`Schedule Baseline` なら `schedule-baseline/`）
- ファイル名は、英小文字、数字、`-` で書く。元の文書にIDがあれば、先頭に付ける（`req-1-mfa.md`、`adr-0001-idp.md`）。議事録は日付から始める（`2026-11-10-weekly.md`）
- 新しい文書は、そのディレクトリの `index.md` に1行のリンクを追加する。新しいディレクトリを作ったら、そのディレクトリの `index.md` を作り、ルートの `index.md` にもリンクを追加する。リンクの行は、ルートの `index.md` と同じ `* [表示名](ファイル名)` の形にする。ディレクトリの `index.md` の見出しは、`init` が作ったものにそろえる。どちらも、手順5の差分に含める

### バンドルに移す場合

- 本文は、元の文書のまま残す。分けた文書では、その件の見出しを最上位（`#`）にする。フロントマターに移した情報（「担当：佐藤」など）を本文から消すかは、利用者に尋ねる
- 1つのファイルをそのまま移すときは、`git mv` で移す。gitが移動として扱うので、履歴をたどれる
- 分けるときや、元の場所に案内を残すときは、gitは移動として扱わない。履歴は元のパスに残ると利用者に伝える
- 分けたファイルの元の場所に案内を残さない場合は、元のファイルを `git rm` で削除する。同じ内容が2か所に残ると、片方だけが更新されてずれるため。削除も、手順5の差分に含めて承認を得る
- 元の場所に、移した先を案内するファイルを残すかを尋ねる。残す場合は、1行の案内だけにする（例：「この文書は [.adaptrace/requirements/](../.adaptrace/requirements/index.md) に移しました。」）
- 元のファイルを指しているリンクや、パスを書いた文を、リポジトリの中から探して（`grep -rn "<元のパス>"`）、一覧にして利用者に知らせる。書き換えるかは、利用者が決める
- 移した後に空になるディレクトリがあれば、知らせる

### 代わりの文書を置く場合

- 代わりの文書を、型ごとのディレクトリに作る。本文には、元のファイルの場所と、何の文書かを短く書く
- `resource` で元のファイルを指す。**パスは代わりの文書からの相対パスで、`./` か `../` から書く**
- SHA-256の記録は、代わりの文書を書いた後に、`adaptrace stale --format json` を実行して得る。その文書の理由（`reasons`）のうち、`kind` が `resource-unrecorded` のものの `current` の値を、`resource_sha256` に書く。この追記は、代わりの文書の差分を承認したときに、あわせて承認されたものとして扱ってよい。差分には「SHA-256は書き込みの後に記録する」と書いておく
- `stale` の値を使う理由：テキストのファイルは、改行コードのCRLFをLFとして計算するので、`sha256sum` の値と違うことがある
- `stale` が `resource-missing` と示したら、パスが誤っているか、ファイルが読めない。パスを確認し、利用者に知らせる

```yaml
type: Requirement
title: 会員サイトの要件定義書
resource: ../../docs/requirements.md
resource_sha256: 3b1c2559…（`stale` が示した64桁）
generated: { by: claude-code/claude-opus-5-5, at: 2026-11-25T10:00:00+09:00 }
```

## 3. 依存関係の候補を選ぶ

取り込んだ文書ごとに、依存関係の候補を選ぶ。本文と、候補の相手の本文を読んで判断する。

### キーの選び方

依存関係は、下流の文書から上流の文書へ書く。基準は「相手が変わったら、この文書を見直すか」。

| キー | 意味 | 例 |
|---|---|---|
| `derived_from` | 相手の内容をもとに作った | 受け入れ基準 → 要件、議事録から起こした決定 → 議事録 |
| `satisfies` | 相手（要件）を満たすためのもの | タスク → 要件、要件を実現するための設計の判断 → 要件 |
| `depends_on` | 相手を前提にしている | リスク → 判断、スケジュール → タスク |

次のキーは、見直しを伝えない。本文や利用者の説明に、はっきりした根拠があるときだけ提案する。

- `supersedes`：この文書が、相手の判断を置き換えた
- `blocks`：この文書が、相手の作業を止めている
- `changes`：変更要求が、相手の文書を変える

### 候補の探し方

- 相手の候補は、バンドルの既存の文書と、今回取り込む文書
- 本文の中のリンク、文書のID（ADR-012、REQ-3など）、同じ用語、「〜に基づき」「〜を前提に」などの表現を手がかりにする
- 代わりの文書は、元のファイル（Excelなど）を読めないことが多い。その場合は、候補を推測せずに、「このファイルは、どの文書が変わったら見直しますか」と利用者に尋ねる。スケジュールなら、タスクやWBSが候補になる
- 逆向きの候補も探す。既存の文書（手順0の `list` に出た文書）のうち、新しい文書に依存すべきもの。これを書くと、既存の文書を変更することになるので、区別して示す

### 候補にしないもの

- 循環依存になるもの。今回の候補と、すでにある依存関係を合わせた計画の上で、相手からこの文書へたどれるなら、依存先にすると循環する。`adaptrace impact` は、バンドルにすでにある文書にしか使えないので、取り込む前の文書は計画の上で判断する。書き込んだ後の `validate` が、循環を最終的に確認する
- 推移的に足りているもの。AがBに、BがCに依存していれば、AからCへは、ふつう張らない。ただし、判断に使ってよいのは、すでにある依存関係と、利用者が採用を決めた依存関係だけ。まだ決まっていない候補を経由して「足りている」と判断しない
- 型が違っても、関係がありそうだからとつながない。たとえば、タスクが設計の判断を前提にしているかは、本文に根拠があるときだけ提案する
- 「関係がある」だけで、相手が変わっても見直さないもの。つなぎすぎると、1つの変更でほとんどの文書が見直しの対象になる。参照したいだけなら、本文のリンクにする

## 4. 利用者と決める

文書ごとに、候補を表で示す。

| 候補 | キー | 根拠 | 確からしさ |
|---|---|---|---|
| `/decisions/auth-provider.md` | `depends_on` | 本文に「IdP-Xを使う前提で」とある | 高 |
| `/requirements/mfa.md` | `satisfies` | タイトルと受け入れ条件が一致 | 中 |

- 根拠には、本文の短い引用か、手がかりを書く
- 候補は、確からしい順に、1文書あたり5件ほどまでにする
- 採否は、選択肢で尋ねる（複数選択）。選択肢が多いときは、何回かに分ける。候補が少ない文書は、いくつかの文書をまとめて1回で尋ね、往復を減らす
- キーの選び方に迷う候補は、どちらのキーにするかも尋ねる
- 利用者が挙げた、候補にない依存関係も受け付ける。その場合も、循環しないかを確認する

## 5. 差分を示して、書き込む

決まった内容を、ファイルごとに差分で示し、承認を得てから書く。承認を得たら、次の順に書く。

1. `git mv` で文書を移す
2. 新しい文書を作り、移した文書と分けた文書にフロントマターを追加する
3. 依存関係を書く。既存の文書への追加も含む
4. `index.md` と `log.md` を更新する
5. 代わりの文書のSHA-256を、`stale` の値で記録する
6. 新しく作ったファイルを `git add` するかを尋ねる。`git mv` した文書はステージされ、新しいファイルは未追跡になるので、そろえておくとコミットしやすい

書くときの決まり：

- パスは、`/` で始めるバンドルの中のパスで書く
- 相手が1件ならスカラー、2件以上ならブロック形式のリストにする
- 既存のフロントマターの行とコメントは残し、キーを追加するだけにする
- 既存の文書に依存関係を追加するだけなら、`generated` は変えない。内容を変えていないため
- `log.md` に、取り込んだことを1行追加するかを尋ねる。追加する場合は、今日の日付の見出し（`## YYYY-MM-DD`）の下に、新しい順で書く。行の形は `* **Creation**: <説明>` にする。`init` が書く `**Initialization**` の行は英語だが、説明の言葉は、それではなく、バンドルの文書の本文と同じ言葉にそろえる

書いた後に、次を実行する。

1. `adaptrace validate`：手順0の時点より増えたエラーがあれば、原因を説明して、修正の差分を示す。SHA-256を記録した後に実行する
2. `adaptrace stale`：新しく張った依存関係のため、古いと示される文書があれば知らせる。依存先の方が新しいためで、見直して変更が要らなければ `verified: { by, at }` を追加する。追加するかは、利用者が決める
3. 上流の文書を1つ選び、`adaptrace impact <文書> --order review` を実行して、並んだ文書が意図どおりかを利用者と確認する。`needs review` が付くのは、その文書より古い文書だけなので、「0 documents to review」でも問題ない。確認するのは、並んだ文書の顔ぶれである

## 6. 報告する

最後に、次をまとめて報告する。

- 取り込んだ文書（移した、代わりの文書を置いた、フロントマターを追加した）
- 張った依存関係と、見送った候補
- `validate` と `stale` の結果
- 利用者が後で決めること（担当者が空の文書、元の場所のリンクなど）

依存関係の図を見たいと言われたら、`adaptrace graph --format mermaid` の出力を示す。
