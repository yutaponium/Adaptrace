# `adaptrace-milestone` の試験

Claude Codeのskill `adaptrace-milestone`（`skills/adaptrace-milestone/`）を、模擬のリポジトリで実行して確認する手順。
skillを修正したら、この試験を実行する。試験の考え方と共通の仕組みは、[`adaptrace-adopt` の試験](../adaptrace-adopt/README.md) と同じ。

## ファイル

| ファイル | 内容 |
|---|---|
| `repo/` | 模擬のリポジトリ。マイルストーン `milestones/release-1.md`（第1期リリース）と、その範囲の作業、要件、未決の変更要求がある |
| `setup.sh` | `repo/` から試験用のgitリポジトリを作り、skillをコピーする。期日（`due`）は、今日からの相対の日付にする（`../render-dates.ts`）。環境変数 `ADAPTRACE_TEST_DAY`（`YYYY-MM-DD`）で、基準の日を指定できる。これは `bun test` で `expected/` と比べるためのもので、`run.ts` で試験するときは、ふつうは指定しない。実行役は、実際の今日の日付で動くため |
| `prompts/runner.md` | 実行役への依頼 |
| `check.ts` | skillを実行した後のリポジトリと、対話の記録を確認する。`must` が1つでも失敗すると、終了コード1 |
| `expected/`、`expected.dialog.md` | 期待する結果と、期待する報告の抜粋。日付は、2026-11-26を基準の日にした値 |
| `failing/`、`failing.dialog.md` | 失敗する例。期日に間に合わない作業を移さずに、作業の期日を書き換え、要件にタスクを作っている。期日の書き換えとタスクの作成は、gitとの比較が要るので、`tests/skills.test.ts` で確認する |

## 第1期リリースの材料と、期待する扱い

| 項目 | 内容 | 期待する扱い |
|---|---|---|
| `requirements/req-2-session-timeout.md` | マイルストーンが直接待つが、満たす作業がない（`uncovered`） | 変更しない。作業が足りないことを報告する |
| `tasks/sms-send.md` | 期日（今日の50日後）がマイルストーン（今日の29日後）より後 | 第2期リリース（`milestones/release-2.md`）に移す |
| `tasks/login-mfa.md` | 終わっていない（`in_progress`、期日は今日の19日後） | そのままにする。報告で残っている作業として示す |
| `change-requests/cr-003-push.md` | 未決で、REQ-1に関わる | 変更しない。報告で触れる |

## 手順

1. skillを実行して、確認する

   ```bash
   bun tests/skills/run.ts adaptrace-milestone /tmp/milestone-test 3 --issues
   ```

2. `check.ts` の失敗と、記録のSkill issuesをもとに、skillを修正する
3. PRの本文の「レビュー」に、合格した回数と、Skill issuesへの採用・不採用を書く
4. 確認項目を変えたら、`expected/` と `failing/` も合わせて修正し、`bun test` が通ることを確認する

## 依頼

```text
第1期リリースに間に合うか判定したいです。残っている作業を整理してください。
```

## 利用者が知っていること

利用者役のエージェントに渡す事実。skillが何をすべきかのヒントは書かない。

- 自分はこのプロジェクトのPMの林
- 第1期リリースの期日は変えられない
- SMSの送信の設定は、送信事業者との契約が第1期リリースの期日に間に合わないので、終わらない。第2期リリースに回す
- ログイン画面のMFA対応は、期日までに終わる見込み。このままでよい
- REQ-2（セッションの有効期限）は、顧客と合意した要件なので、外せない。作業のタスクは、来週、担当を決めてから自分で作る
- CR-003（プッシュ通知）は、来週の変更管理委員会で判断する。今は変えないでほしい
- 第1期リリースは、まだ終わっていない
- 差分は、内容が上の事実と合っていれば承認する
- `log.md` には、決めたことを記録してよい
- コミットは、自分で確認してから行うので、しないでほしい

## 確認項目（`check.ts`）

- `must`
  - `validate` のエラーが0件
  - 第1期リリースが、SMSの送信の設定を待っていない（`depends_on` にない。タスクの `blocks` も第1期リリースを指さない）
  - 第2期リリースが、SMSの送信の設定を待っている。第2期リリースが待つのは、自分の作業とSMSの送信の設定だけで、マイルストーンに `blocks` を追加していない
  - 第1期リリースは、ほかの作業とREQ-2を待ち続けている。第2期リリースも、自分の作業を待ち続けている
  - 第1期リリースの `due` が変わっていない。`state` を追加していない
  - 第1期リリースと第2期リリースで変わったのは、`depends_on` と `blocks` だけ。SMSの送信の設定で変わってよいのは、第2期リリースを指す `blocks` だけ。ほかの文書（要件、タスク、変更要求、`index.md`）は変更していない。新しい文書も作っていない。`log.md` は追加だけ
- `should`
  - 2つのマイルストーンと、SMSの送信の設定の `generated` が変わっていない
  - 報告で、作業が足りないREQ-2に触れている
  - 報告で、未決のCR-003に触れている
  - 報告で、残っている作業（ログイン画面のMFA対応）に触れている
