# `adaptrace-change-request` の試験

Claude Codeのskill `adaptrace-change-request`（`skills/adaptrace-change-request/`）を、模擬のリポジトリで実行して確認する手順。
skillを修正したら、この試験を実行する。試験の考え方と共通の仕組みは、[`adaptrace-adopt` の試験](../adaptrace-adopt/README.md) と同じ。

## ファイル

| ファイル | 内容 |
|---|---|
| `repo/` | 模擬のリポジトリ。Adaptraceを導入済みのバンドルに、未決の変更要求 `cr-001` がある。社内の業務部門から受けた、コードを認証アプリだけにする依頼である。`inbox/` に、顧客A社からの依頼のメール（SMSでもコードを受け取りたい）がある |
| `setup.sh` | `repo/` から試験用のgitリポジトリを作り、skillをコピーする。コミットの日付は2026-11-15に固定する |
| `prompts/runner.md` | 実行役への依頼 |
| `check.ts` | skillを実行した後のリポジトリと、対話の記録を確認する。`must` が1つでも失敗すると、終了コード1 |
| `expected/`、`expected.dialog.md` | 期待する結果と、期待する報告の抜粋 |
| `failing/`、`failing.dialog.md` | 失敗する例。起点がない、受け付けた日時が違う、承認済みにしている、連絡先を書いている、重なりを報告していない |

## 手順

1. skillを実行して、確認する

   ```bash
   bun tests/skills/run.ts adaptrace-change-request /tmp/cr-test 3 --issues
   ```

2. `check.ts` の失敗と、記録のSkill issuesをもとに、skillを修正する
3. PRの本文の「レビュー」に、合格した回数と、Skill issuesへの採用・不採用を書く
4. 確認項目を変えたら、`expected/` と `failing/` も合わせて修正し、`bun test` が通ることを確認する

## 依頼

```text
inbox/2026-11-20-sms.eml の依頼を、変更要求として受け付けてください。
```

## 利用者が知っていること

利用者役のエージェントに渡す事実。skillが何をすべきかのヒントは書かない。

- 自分はこのプロジェクトのPM。顧客A社から開発を請け負っている
- 山田さんは、顧客A社 情報システム部の担当者で、発注者の窓口。バンドルには、まだ顧客A社の情報がない
- 顧客A社 情報システム部は、ステークホルダーとして記録してよい。IDは `a-corp`
- メールは、2026年11月20日に受け取った。受け取ったのは、メールの `Date:` の日時
- 変更要求は、受け付けた時点では `submitted` にしている。承認するかは、まだ決めていない
- SMSの送信を、どの事業者に頼むかは決めていない
- 社内では、業務部門から「コードは認証アプリだけにする」という依頼を受けていて、まだ決めていない
- 重なる変更要求があれば、まず社内で協議したい。会議の準備の材料は見たいが、ファイルにするかは中身を見てから決める
- 工数の目安は、規模の感じがつかめればよい
- 差分は、上の事実と合っていれば承認する
- `log.md` には、受け付けたことを記録してよい
- コミットは、自分で確認してから行うので、しないでほしい

## 確認項目（`check.ts`）

- `must`
  - `validate` のエラーが0件
  - 新しい変更要求が1件だけあり、`changes` に `/requirements/req-1-mfa.md` がある
  - `received_at` が、メールの `Date:` の日時（`2026-11-20T10:15:00+09:00`）
  - `state` が `submitted`
  - `requested_by` が、ステークホルダーの文書を `/` から指している。その文書は `side: customer`
  - バンドルのどのファイル（`log.md`、`index.md` を含む）にも、メールアドレスと電話番号がない
  - 既存の文書（`index.md`、`log.md` を除く）を変更していない。`setup.sh` が作った最初のコミットと比べる
  - 報告の表で、`cr-001` との組の判定が `conflict`。skillは、重なる組の判定を1組1行の表で示す。`cr-001` を含む行の判定の列が `conflict` であることを確認する
- `should`
  - 依頼者のステークホルダーの文書に `role` がある
  - 新しい文書（変更要求、ステークホルダー、`meeting --write` で作った会議の下書き）が、ディレクトリの `index.md` からリンクされている。そのディレクトリの `index.md` も、ルートの `index.md` からリンクされている
  - 見積もりの前提を、利用者に確認している
  - 報告に、人時での工数の目安がある
  - 報告に、期日に響くマイルストーン（年内リリース）がある
