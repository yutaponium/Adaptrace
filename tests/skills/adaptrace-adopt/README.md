# `adaptrace-adopt` の試験

Claude Codeのskill `adaptrace-adopt`（`skills/adaptrace-adopt/`）を、模擬のリポジトリで実行して確認する手順。
skillを修正したら、この試験を実行する。

## 試験の2つの層

LLMがskillを読んで判断するので、同じ入力でも結果は毎回少しずつ変わる。そのため、試験を2つの層に分ける。

| 層 | 内容 | いつ実行するか |
|---|---|---|
| LLMを使わない部分 | `check.ts` が、期待する結果（`expected/`）に合格し、失敗する例（`failing/`）に不合格を出す。`setup.sh` が試験用のリポジトリを作れる（`tests/skills.test.ts`） | `bun test` で毎回。CIでも実行する |
| skillの実行 | `../run.ts` が、Claude Code（`claude -p`）にskillを実行させ、結果を `check.ts` で確認する | `skills/adaptrace-adopt/` を変更したとき。手で実行する |

## ファイル

| ファイル | 内容 |
|---|---|
| `repo/` | 模擬のリポジトリ。要件定義書（1ファイルに2件）、ADR2件、議事録（宿題とリスクを含む）、Excelのスケジュール（ダミー）、READMEからのリンク |
| `setup.sh` | `repo/` から試験用のgitリポジトリを作り、skillをコピーする。コミットの日付は2026-11-10に固定する |
| `prompts/runner.md` | 実行役への依頼 |
| `../run.ts` | すべてのskillで共通の実行役。試験用のリポジトリを作り、実行役と利用者役の2つのエージェント（`claude -p`）でskillを実行し、`check.ts` で確認する。これを指定した回数（既定3回）くり返す |
| `../prompts/` | すべてのskillで共通の指示。`runner-system.md` は実行役が質問したら止まるための決まり、`user.md` は利用者役への指示。どちらのエージェントに何を見せるかは、ここで確認できる |
| `check.ts` | skillを実行した後のリポジトリを確認する。`must` が1つでも失敗すると、終了コード1 |
| `expected/` | 期待する結果。2回目の試験の結果を、人が確認して修正したもの |
| `failing/` | 失敗する例。修正前のskillで実行した結果。議事録から文書を起こしておらず、日時も失われている |

## 手順

1. skillを実行して、確認する。回数は、結果のばらつきを見るため3回を目安にする。1回に数分かかり、Claude Codeの利用料がかかる

   ```bash
   bun tests/skills/run.ts adaptrace-adopt /tmp/adopt-test 3 --issues
   ```

   - 3回は同時に実行する。同時に実行する数は `--jobs` で変えられる
   - `--issues` を付けると、回ごとに、実行役が感じたskillの不明な点（Skill issues）を `run-<回>.issues.md` に記録する。skillを修正した直後に付ける。修正後の確認だけなら省いてよい。1回あたり約50秒と、利用料の約3分の1を節約できる
   - 回ごとに、所要時間の内訳を `run-<回>.timing.json` に記録し、要約を表示する。時間のほとんどは、モデルの応答待ちである

   - 2つのエージェントを使う。実行役は、skillを実行し、質問したら止まる。利用者役は、下の「利用者が知っていること」だけを見て、質問に答える。`run.ts` が2つの間で質問と答えを受け渡し、実行役の会話は `--resume` で続ける
   - 実行役には、「利用者が知っていること」も `check.ts` も `expected/` も見せない。利用者役にも、確認項目は見せない
   - 利用者役は、事実で答えられない質問には `UNCOVERED` を付けて答える。質問が分かりにくい箇所や、「利用者が知っていること」の不足が分かる
   - 回ごとに、`run-<回>.dialog.md` に質問と答えが記録される
   - 人が試す場合は、`setup.sh` で作ったリポジトリでClaude Codeを起動し、下の「依頼」を入力して、「利用者が知っていること」に沿って答える。最後に `bun tests/skills/adaptrace-adopt/check.ts <リポジトリ>` を実行する
2. `check.ts` の失敗と、記録のSkill issuesをもとに、skillを修正する。採用するかどうかは、1件ずつ決める
3. PRの本文の「レビュー」に、合格した回数と、Skill issuesへの採用・不採用を書く。記録そのものは、リポジトリに入れない。実行のたびに変わり、量も多いため
4. 確認項目を変えたら、`expected/` と `failing/` も合わせて修正し、`bun test` が通ることを確認する

## 依頼

```text
docs/ と pm/schedule.xlsx をAdaptraceで管理したい。依存関係も張って
```

## 利用者が知っていること

利用者役のエージェントに渡す事実。`run.ts` は、この節だけを利用者役に渡す。実行役には渡さない。
skillが何をすべきかのヒントは書かない。書くのは、実際の利用者なら知っている事実と好みだけにする。ヒントを書くと、skillの手順に不足があっても、試験が合格してしまう。

- プロジェクトの名前は「会員サイト」
- 作業は、今のブランチのままでよい。コミットは、自分で確認してから行うので、しないでほしい
- `docs/requirements.md` は、今後はAdaptraceで管理したい。要件は1件ずつ分けて管理したい。元の場所には、移した先の案内を残したい
- `docs/adr/` のADRと、`docs/minutes/` の議事録も、今後はAdaptraceで管理したい。元の場所に案内は要らない
- `pm/schedule.xlsx` は、今後もExcelで管理する。中身は、タスクごとの日程の表。今はログイン画面のMFA対応（田中、2026年12月15日まで）だけが入っている
- 人：佐藤（ID `sato`）は要件の担当。田中（ID `tanaka`）は開発の担当。gitのコミットの作者 `test` は、チームの共有アカウント。元の文書を書いた人の記録は、`human:test` でよい。それ以外の担当者は決まっていない
- 議事録の宿題（ログイン画面のMFA対応）は、まだ始めていない。IdP-Xのリスクは、今のところ監視しているだけ
- 議事録は2026年のもの
- 要件が変わったら、その要件を実現するための設計の判断とタスクは見直す。判断が変わったら、その判断を前提にしたリスクは見直す。タスクの内容や期日が変わったら、スケジュールを見直す
- 議事録から起こした宿題やリスクは、議事録の内容が訂正されたら見直す
- 依存関係の候補は、根拠を見て、上の事実に合うものだけを採用する。迷うものは採用しない
- 差分は、上の事実と合っていれば承認する
- `log.md` には、取り込んだことを記録してよい
- 見直しの記録（`verified`）は、今回は追加しない
- 移した文書を指しているリンクは、今回は書き換えない
- LLMのコマンドは用意していない

## 確認項目（`check.ts`）

`must` は、skillが必ず満たすべき項目。`should` は、利用者の選び方で変わるので、警告だけにする。

- `must`
  - `validate` のエラーが0件
  - 要件定義書が、2件のRequirementに分かれている
  - ADR-0001がREQ-1に、ADR-0002がREQ-2に、見直しを伝えるキーで依存している
  - 移したADR-0001の `generated.at` が、元ファイルの最終コミットの日付（2026-11-10）と同じ
  - 議事録がMeetingになり、宿題がTaskに、リスクがRiskになって、それぞれ `derived_from` で議事録を指している
  - Excelの代わりの文書があり、`resource_sha256` を記録している
  - `stale` が何も示さない
- `should`
  - REQ-1の担当者が `sato`、Taskの担当者が `tanaka`、期日が12月15日
  - 移した文書の `generated.by` が人（`human:`）
  - Taskに `state` がある
  - TaskがREQ-1に、RiskがADR-0001に依存している
  - スケジュールの代わりの文書が、Taskに依存している
  - ディレクトリの `index.md` に、すべての文書へのリンクがある
