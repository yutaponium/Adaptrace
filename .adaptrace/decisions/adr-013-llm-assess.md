# LLMによる影響の判定は、ユーザーが指定するコマンドを呼んで行う

> 注：2026-11-23に文言だけを修正した。決定の内容は変えていない。

## 決定

- `accordant assess <文書>` で、変わった文書の直接の依存元ごとに「その依存元を最後にコミットしたときから、依存先の何が変わったか」をgitの差分で示す。LLMがなくても使える
- `--llm <コマンド>`（または環境変数 `ACCORDANT_LLM`）を渡したときだけ、LLMに判定させる。コマンドはシェルで実行し、プロンプトを標準入力に渡して、標準出力のJSONを読む。JSONのキーは `verdict`（`none` / `minor` / `major`）、`reason`、`body`
- 判定は更新案になるだけで、ファイルには書き込まない。`none` には `generated` だけを更新する案（見直した記録）を、`minor` と `major` には新しい本文の案を付ける
- コマンドはCLIの引数か環境変数からだけ受け取る。バンドルやリポジトリの設定ファイルからは読まない
- 対象は直接の依存元だけにする。間接の依存元は、直接の依存元を更新してから、その文書について実行する
- MCPでは、同じ材料を `assess_context` で返し、判定はエージェント自身が行う。判定結果の適用には `propose_update` を使う

## 理由

- 設計原則「特定のLLMやエージェントに依存しない」に合わせる。標準入出力でやり取りするコマンドなら、`claude -p`、`ollama run <model>`、`llm` など何でも使える。APIキーやSDKへの依存をAccordantに持ち込まない
- 設計原則「ユーザーの文書を勝手に書き換えない」に合わせ、判定は提案に留める
- 基準の版は、依存元の `generated.at` より前のコミットではなく、依存元を最後に変更したコミットから取る。文書は書いてからコミットするのが普通で、日時で探すと見つからないことが多いため
- クローンしたリポジトリの設定でコマンドを指定できると、開くだけで任意のコマンドが実行される危険がある
- 間接の依存元は、間にある文書が変わるかどうかで判定が変わるので、1段ずつ進める方が判定が正確になる

## 検討した他の案

- 特定のLLMのAPIを呼ぶ：手軽だが、特定の提供元に依存する
- OpenAI互換のHTTP APIを呼ぶ：多くの提供元で使えるが、APIキーの扱いとHTTPの実装を抱える
- MCPのsamplingでクライアントのLLMに頼む：依存は増えないが、対応しているクライアントが限られる
- 間接の依存元もまとめて判定する：一度で済むが、間の文書の更新を待たずに判定することになる
