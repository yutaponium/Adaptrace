# 要件の充足は、CLIの `coverage` で依存関係から計算し、マイルストーンの範囲は待っている文書をたどって決める

## 決定

- 要件ごとに、満たす文書（`satisfies`）と、その進み具合を示す `adaptrace coverage [bundle]` と、MCPのツール `coverage` を追加する。名前は、メンテナーの確認を得て決めた。決めたのは2026-11-26
- 要件の状況は3つにする
  - `uncovered`：数える文書のうち、要件を `satisfies` で指すものがない
  - `open`：数える文書のうち、終わっていないものがある
  - `covered`：それ以外
- 満たす文書が終わったかは、型で決める
  - Task：`state` の値で決める。既定は `done` で、`--done` で変えられる。大文字と小文字は区別しない。`state` の値の一覧が未確定のため、`conflicts` の `--settled` と同じ形にする
  - 要件の型の文書：その要件が `covered` かどうか。要件を細分した要件で満たす書き方に対応するため
  - Milestone：そのマイルストーンの範囲にTaskがあり、すべて終わったかどうか。作業のないマイルストーンは、終わったとみなさない
  - それ以外（Decisionなど）：あれば満たしているとみなす。型ごとに `state` の意味が違うため
- 要件の型は、既定で `Requirement` とし、`--type` で変えられる
- `--milestone <文書>` を付けると、マイルストーンの範囲だけを示す。文書は、廃止していない `type: Milestone` の文書に限る。範囲を依存関係でたどることは、メンテナーの確認を得て決めた（2026-11-26）
  - 範囲は、マイルストーンが待っている文書（`depends_on` と `blocks`）から始めてたどる。向きは `board` と同じにする
  - TaskとMilestoneからは、それが待っている文書をたどる。要件からは、それを満たすTaskと要件をたどる。マイルストーンが要件を待っているなら、その要件の作業もマイルストーンの範囲になるためである
  - それ以外の文書（判断など）は範囲に入れるが、その先はたどらない。要件の導出（判断が要件に依存するなど）まで、範囲を広げないためである
  - `status: deprecated` の文書は、範囲に含めず、その先もたどらない
  - 示す要件は、範囲の要件と、範囲のTaskとMilestone（マイルストーン自身を含む）が満たす要件にする
  - 範囲の外のTaskとMilestoneは、要件の進み具合に数えない。次のリリースの作業が残っていても、このマイルストーンの判定には響かないようにするためである
  - 示す要件は、範囲の中の作業だけで状況を決める。示さない要件が、示す要件を満たしている場合は、その要件について作業をすべて数える。範囲外の作業を数えないと、終わっている要件まで `uncovered` になるためである
- `--milestone` のときは、範囲の作業（Task）を、担当者、期日、終わったか、マイルストーンより後の期日か（`late`）とともに示す
- 何も書き込まない。終了コードは0
- `--format` は `text`、`markdown`、`json`。`markdown` は `--link-base` に対応する

## 理由

- マイルストーンの判定（skillの候補）には、要件ごとの充足の計算が要る。ADR-026に従い、計算はCLIに作る
- 要求事項トレーサビリティ・マトリックスを、別の表として管理しない方針（`docs/guide/pmbok.md`）と合う。表は依存関係から毎回計算する
- マイルストーンを指定しない形でも使えるので、バンドル全体のトレーサビリティの確認にも使える
- 範囲を依存関係でたどれば、今のバンドルの書き方（マイルストーンがタスクに依存する）のまま使える。要件を直接 `depends_on` で指したマイルストーンでも、その要件が範囲に入る

## 検討した他の案

- マイルストーンの判定に必要な情報（未決の変更要求を含む）を1つにまとめる `adaptrace milestone <文書>`：用途が限られる。未決の変更要求は `conflicts` の `requests[].reach` と範囲を照らせば分かる
- マイルストーンの範囲を、マイルストーンが直接 `depends_on` で指す要件だけにする：既存のバンドルに書き足す必要がある
- Task以外も `state` で進み具合を判定する：型ごとに `state` の意味が違い（Decisionの `accepted` など）、値の一覧も未確定である
