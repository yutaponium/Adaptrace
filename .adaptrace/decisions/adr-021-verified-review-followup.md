# 見直しの記録で、gitの日時をgeneratedに書き込まない

ADR-020のうち、次の2つをこの決定で置き換える。ADR-020のほかの決定は変えない。

- 「`generated` がなく、gitの日時を内容の最終更新にしている文書に `verified` を追加するときは、そのときの最終更新を `generated: { by: process:git, at }` として書き込む」
- 「内容の日時がなく、`verified` だけがある文書は、`verified.at` を内容の最終更新としても使う」

## 決定

- 見直しを記録するとき、gitの日時を `generated` に書き込まない。`assess` とMCPの更新案は、`verified` の行だけを変える
- 下流の文書を古くしない効果は、`generated.at`（または古い `timestamp`）を持つ文書にだけ働く。gitの日時だけの文書では、`verified` を追加したコミットで最終更新が進み、これまでどおり下流の文書が見直しの対象になる
- 内容の日時がなく、`verified` だけがある文書は、最も古い `verified.at` を内容の最終更新として使う。最も新しい `verified.at` を、見直した日時として使う
- `verified` を追加するときは、既存の行とコメントを残し、新しい `- { by, at }` の行を追加する。1行の `verified: { ... }` は、その行と新しい行のリストにする
- 追加した結果、それまでの記録と新しい記録がそろって読めないとき、または `verified` のキーが2つになるときは、更新案を作らずにエラーにする。引用符で囲んだキーなどが当たる
- MCPの `propose_update` の `review: true` は、空の `set` と `unset` を、指定していないものとして扱う

## 理由

- gitの日時を書き込むと、その文書は以後、gitの日時を使わなくなる。本文を変えてコミットしても、内容の最終更新が動かず、下流の見直しがもれる。作業ツリーの未コミットの変更も、最後のコミットの日時にしてしまう
- gitの日時だけの文書で下流に連鎖するのは、ADR-010の動作と同じで、見直しのもれは起きない。もれを起こす方式より、連鎖が残る方が安全である
- `verified` だけの文書で最も新しい日時を内容の最終更新にすると、見直すたびに下流が古くなる。ADR-020が防ごうとした連鎖そのものである
- 見直しの記録は、PMにとって残しておきたい記録である。コメントも含めて、既存の行を変えない方がよい。記録が失われるくらいなら、案を作らない方がよい

## 検討した他の案

- gitの履歴から、`verified` だけを変えたコミットを除いて最終更新を求める：gitの日時だけの文書でも効果が働くが、コミットごとに差分を読む必要があり、処理が重い
- 見直しの記録を、`generated` を持つ文書に限る：分かりやすいが、gitの日時だけの文書で見直しを記録する手段がなくなる
