# Markdown以外のファイルは、OKFのresourceとsourcesで指し、SHA-256で変更を知らせる

## 決定

- ExcelのWBSやMS Projectのスケジュールなど、Markdown以外のファイルは、それを表す「代わりの文書」をバンドルに置く。代わりの文書から、OKFのキーでファイルを指す
  - `resource`：その文書が表しているファイル
  - `sources[].resource`：その文書のもとにしたファイル
- 代わりの文書を見直した時点で、ファイルの内容からSHA-256を計算して記録する。`resource` には `resource_sha256`、`sources` の各項目には `sha256` を使う。値は16進数64桁で、小文字で書く。大文字も読み、大文字と小文字を区別せずに比べる
- テキストのファイルは、改行コードのCRLFをLFとして計算する。テキストかどうかは、先頭の8000バイトにNULがないかで決める。gitが `core.autocrlf` でテキストとみなすファイルは、ふつうこの規則でもテキストになる。`core.autocrlf` で改行コードが変わっても、同じ値になるようにするため
- `stale` は、ファイルの今のSHA-256を記録と比べる
  - 違えば、理由 `resource-changed` で列挙する
  - 記録がなければ、理由 `resource-unrecorded` で列挙する
  - ファイルがないか、通常のファイルでない（ディレクトリなど）か、読めなければ、理由 `resource-missing` で列挙する。移動や削除で、追跡が黙って止まらないようにするため
  - `resource-changed` と `resource-unrecorded` では、今のSHA-256を示す。見直したら、その値を記録すれば消える
- 日時もgitも使わない
- MCPの `propose_update` は、`review: true` のとき、`verified` に加えてSHA-256も今の値に更新する。内容を変える案では、`resources: true` を指定したときに更新する。このときは、`set` と `unset` を適用した後のフロントマターから計算する
- ローカルのファイルとして扱うのは、`./` か `../` で始まる相対パス（その文書のディレクトリから読む、OKF §6.2）と、`file:///` で始まる絶対のURIだけにする。`\` は `/` として読む。バンドルの外のファイルも指せる
- それ以外の値は、ファイルとして扱わない。`/` で始まる値、`pm/schedule.mpp` のような値、URL、リソース名（`projects/...`、`/subscriptions/...`）、説明の文などである。`resource` と `sources` には、こうした値も書けるため
- 同じファイルを複数回指していても、1つとして扱う
- `validate` は、指しているファイルが存在しないか通常のファイルでないとき `missing-resource`、記録したSHA-256が文字列でないか形が正しくないとき `invalid-sha256`、記録があるのに指す値がローカルのファイルとして読めないとき `unlinked-sha256` の警告を出す
- `status: deprecated` の文書は、`stale` でも `validate` でも調べない
- `impact` と `progress` は変えない。代わりの文書を見直して更新すると、依存関係をたどって下流に伝わる

## 理由

- 代わりの文書の `generated.at` を手で更新する運用では、実際のファイルを更新して代わりの文書の更新を忘れると、変更に気づかない
- OKFは、`resource` を「その概念が表している実体」、`sources` を「概念のもとにした資料」と定めている。指すためのキーは、独自に作らずに済む（設計原則2）。記録のためのキーは、OKFが認める追加のキーとして加える
- 内容のハッシュなら、「見直したときのファイルと同じか」を正確に判定できる。日時で判定する方式を実装して検討したが、次の場合に誤った
  - cloneやCIでは、ファイルの更新日時がcheckoutの日時になる
  - shallow cloneでは、すべてのファイルが最新のコミットの日時になる
  - rebaseやcherry-pickで取り込んだ変更は、author dateが古いまま残る
  - 「ファイルを編集し、文書を見直し、両方をコミットする」と、コミットの日時が見直しの日時より後になる
- 記録がない文書を `stale` に出すのは、記録を始めるきっかけにするためである。`stale` は常に終了コード0なので、CIは止まらない
- ハッシュは利用者が手で計算しなくてよいよう、`stale` が今の値を示し、MCPの更新案に含める。適用は人が決める（設計原則6）
- `stale` とMCPは、文書や呼び出し側が指すファイルのSHA-256と有無を返す。バンドルの外のファイルも対象になる。Accordantは利用者の手元で動き、利用者が使うエージェントにだけ応答するので、この点は受け入れる。ファイルの中身は返さない。大きなファイルも、少しずつ読んで計算する

## 検討した他の案

- 値の形から、ファイルかどうかを推測する（拡張子がある、`/` を含む、など）：一度実装したが、`projects/p/topics/orders.v1` や `/subscriptions/...` のようなリソース名を誤ってファイルとして扱った。SHA-256の記録は利用者が明示的に行うので、書き方の決まりを1つにする方が予測しやすい
- 独自のキー（`source`）でファイルを指す：提案書の案。OKFに同じ意味のキーがあるので、設計原則2に反する
- ファイルの日時（gitのauthor dateと更新日時）と、文書の見直した日時を比べる：利用者が記録するものはないが、上に書いた場合に誤る。一度実装して、やめた
- コミットの順番で比べる（文書の最後のコミットより後に、ファイルを変えたコミットがあるか）：cloneやrebaseに強いが、文書を誤字の修正などでコミットすると、見直していなくても消えてしまう
- OKFの `sources[].last_modified` を使う：ファイルの日時を手で書く必要があり、日時の方式と同じ問題がある
