# 変更要求が変える文書はchangesで指し、影響範囲が重なる未決の変更要求を示す

ADR-016のうち、「変更要求の文書に、変える文書を書くキーは追加しない」を、この決定で置き換える。ADR-016のほかの決定は変えない。

## 決定

- 依存関係のキーに `changes` を追加する。変更要求から、その変更要求が直接変える文書（起点）を指す
  - ほかのキーと同じく、`validate` で相手を検証し、`graph` に出す
  - 見直しの連鎖は伝えない（`blocks`・`supersedes` と同じ）。`impact`、`stale`、`progress` はたどらない。承認されていない変更要求で、ほかの文書が古くならないようにするため
- 承認したら、これまでどおり、起点の文書に `derived_from` で変更要求を追加する。`progress` の起点は `derived_from` で決める（ADR-018のまま）
- `accordant conflicts [bundle]` を追加する。未決の変更要求のうち、影響範囲が重なる組を示す
  - 未決の変更要求：`changes` を持ち、`status: deprecated` でなく、`state` が決着した値でない文書。決着した値は、既定で `approved`、`accepted`、`rejected`、`deferred`、`implemented`、`closed`、`done`。大文字と小文字は区別しない。`--settled` で変えられる
  - 型は見ない。型の一覧が未確定のため。`changes` を持たないか、`changes` の文書がすべて `deprecated` の未決の変更要求は、比べられなかった変更要求として示す
  - 影響範囲：起点と、起点から `impact` と同じ向きにたどって届く、`deprecated` でない文書
  - 組ごとに、両方が変える文書（同じ起点）と、両方が届く文書を示す。同じ起点を持つ組を先に並べ、その中では重なりの大きい組から並べる
  - 出力は `text`・`markdown`・`json`。終了コードは0。何も書き込まない
- `estimate` は、起点の文書を渡さず `--request` だけを渡したとき、その変更要求の `changes` を起点にする。`deprecated` の文書は「Left out as deprecated」に示す。MCPの `estimate_context` も同じ
- MCPに、読み取りのツール `conflicts` を追加する
- 矛盾しているかどうかのLLMによる判定と、協議の会議の準備は、後の段階で扱う（候補7の段階B、C）

## 理由

- 矛盾する変更要求を見つけるには、承認の前に、変更要求がどの文書を変えるかが分かる必要がある。今は承認の後に `derived_from` を張るので、承認の前には分からない
- `estimate` の引数で起点を渡す方式では、変更要求ごとに起点を覚えておく必要があり、記録も残らない。キーにすれば、変更要求の文書を見れば分かる
- 承認の前から起点に `derived_from` を張ると、承認されていない変更要求で下流が古くなる。`progress` の起点の意味も変わる。見直しの連鎖を伝えないキーにすれば、どちらも起きない
- `state` の値は未確定なので、決着した値を既定で持ち、変えられるようにした。既定の値は、ガイドで変更要求の `state` の例に挙げた値に合わせた
- 影響範囲が重なるだけで矛盾とは限らない。まず確実に分かる重なりを示し、内容の判定は人かLLMに任せる（設計原則5）

## 検討した他の案

- キーを追加せず、`estimate` と同じく引数で起点を渡す：スキーマは変わらないが、変更要求が増えると引数が長くなり、記録も残らない
- 承認の前から、起点の文書に `derived_from` を張る：キーは増えないが、承認の前から下流が古くなる
- `changes` を見直しの連鎖を伝えるキーにする：変更要求を更新すると起点が古くなり、意味が逆になる
- 未決の値を指定する（`--open submitted,proposed`）：プロジェクト独自の値では、指定が必要になる
